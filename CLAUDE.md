# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

WinSysLive is a native Win32 GUI app (C++23, ATL/WTL, Unicode) at an early stage: a WTL frame window hosting a tabbed view. The app code lives in `WinSysLive/`; the heavy lifting comes from two git submodules by the same author, each with its own `CLAUDE.md` to read before changing it:

- `wtlhelper/`: WTL UI libraries. `WTLHelper` (static lib: dark mode, `Settings`, list-view/tab helpers, vendored WTL headers in `WTL/`) and `GraphControl` (Direct2D time-series graph) are both projects in `WinSysLive.sln`.
- `winsys/`: the `WinSys` static library (NT native API wrappers: processes, threads, `ProcessManager<>` snapshots, services, network interface and drive statistics, and so on). The app references it, along with WTLHelper, TreeListView, GraphControl and HexControl (`<HexControl/SimpleHexControl.h>`, a static lib in `wtlhelper/HexControl`).

If the submodule directories are empty, run `git submodule update --init`.

## Build

MSBuild only. There is no CMake, lint, or test setup for the app itself. Toolset v145 (VS 18).

```powershell
msbuild WinSysLive.sln /p:Configuration=Debug /p:Platform=x64 /m
msbuild WinSysLive\WinSysLive.vcxproj /p:Configuration=Debug /p:Platform=x64   # app + WTLHelper (project reference)
```

ReleaseSigned (x64) is Release with the exe signed after the build, as TotalPE does (`signtool sign /a /n Scorpio /t http://timestamp.digicert.com /fd sha256`, after the DbgHelp copy, so a failed signing fails the build). Build it through the solution (`msbuild WinSysLive.sln /p:Configuration=ReleaseSigned /p:Platform=x64`), which builds the libraries in Release; building the project alone would ask them for a ReleaseSigned they don't have. The output is `x64\ReleaseSigned\`.

Dependencies come from the submodules. WTLHelper needs its NuGet packages (Detours, WIL, wtl), restored with `nuget restore wtlhelper\WTLHelper.sln`. WinSys needs phnt and WIL from vcpkg (user-wide integration) and must stay pinned to Windows SDK `10.0.26100.0` (see `winsys/CLAUDE.md` for why). `dbghelp.dll` is delay-loaded and loaded from the exe's folder (see Symbols); the build doesn't put it or `symsrv.dll` there (the Pavel Tools installer ships the Debugging Tools' copies beside the exe), so a dev build without them uses the system's `dbghelp.dll`, which can't download symbols. Copy both from `$(WindowsSdkDir)Debuggers\x64` into the output folder to test the symbol server.

Include paths are `..\wtlhelper\WTLHelper` and `..\wtlhelper\WTL` (WTLHelper headers such as `WTLHelper.h`, `Settings.h` and `NativeCustomTabView.h` are included by bare name), plus `..\wtlhelper` and `..\winsys` so that the other libraries are included with a folder prefix: `<WinSys/ProcessManager.h>`, `<TreeListView/include/TreeListView.h>`. Keep that prefix. WinSys and WTLHelper both have a `SecurityHelper.h`, and WTLHelper has its own, different `TreeListView.h`. The CRT is linked statically (`MultiThreaded[Debug]`).

The include order in `pch.h` matters, and the reasons are commented there:
1. Full `windows.h` first (with `WIN32_NO_STATUS`), because `phnt_windows.h` forces `WIN32_LEAN_AND_MEAN`.
2. `phnt_windows.h`, then `#undef INITGUID`.
3. ATL/WTL.
4. `phnt.h` last, because it `#define`s `TOKEN_INFORMATION_CLASS` values that break `atlcom.h`.

`winsock2.h` comes right before `windows.h`, which would otherwise include `winsock.h`, whose definitions clash with `ws2def.h` (needed by `ws2ipdef.h`, which `iphlpapi.h` needs for its IPv6 tables).

`NOMINMAX` is defined at the top of `pch.h`; phnt would define it, but too late now that `windows.h` comes first.

## Architecture

- **WinSys first:** core Windows functionality (native API queries, process/thread/handle operations, GPU, connections, symbols, dumps) belongs in WinSys, exported as types the app consumes; the app keeps UI state and UI-only types (highlighting, rows, icons, threading for the UI). When a feature needs a new query, add it to WinSys (see `winsys/CLAUDE.md`) rather than calling the API from a view.
- `WinSysLive.cpp`: `_tWinMain` initializes COM and `CAppModule _Module`, loads settings from the registry key `Software\ScorpioSoftware\WinSysLive`, calls `WTLHelper::InitDarkMode(...)` *before* any window is created, then runs the message loop with a single `CMainFrame`.
- `AppSettings.h`: a `Settings` subclass declared with WTLHelper's `BEGIN_SETTINGS`/`SETTING`/`DEF_SETTING` macros. The first constructed instance becomes the singleton (the global `AppSettings _Settings` in `WinSysLive.cpp`) and is reached anywhere through `AppSettings::Get()`. To add a persisted option, add a `SETTING(...)` entry plus a `DEF_SETTING(...)` accessor, and call `Save()` after changing it. At logoff or shutdown no window is destroyed, so the frame's `WM_ENDSESSION` calls `IView::SaveSettings` on every view (a view that saves state in `WM_DESTROY`, such as column layouts, does the same there) and then saves the frame's own.
- `MainFrm.*`: `CMainFrame` (`CFrameWindowImpl` + `CAutoUpdateUI`, and it implements `IMainFrame`) hosts the tabs in `CMainTabView`, a `CNativeCustomTabViewImpl`. Only Processes is always open (its page is `FixedPage`, whose close button `CalcCloseButtonRect` makes empty); the others open and close: the `Tabs` setting has the open ones' keys (`s_Tabs`, which must not change) in tab order (default Processes, Performance, Services), saved as tabs open and close and at exit (dragging reorders them), and `ActiveTab` is an index among them. A View menu command (also a checked toolbar button) opens a closed tab, activates an open one, and closes the active one; `TBVN_TABCLOSEBTN` closes through the tab view, which destroys the view's window (the view deletes itself). Pages are matched to views by their windows (`GetPageView`), never by index, and the active view is kept as a pointer, as removing and dragging tabs shift the indices; `ForgetView` stops the frame talking to a view before its page goes. `ActivateTab` opens a closed tab (Go to Kernel Module, Go to Driver); a view opened after startup gets the theme and font from `OpenTab`. Dark mode is toggled through `WTLHelper::SwitchToMode`, after which every thread window is redrawn and the status bar background is set by hand.
- Views follow TotalPE (`C:\dev\totalpe2\totalpe`):
  - `Interfaces.h` declares `IMainFrame` and `IView`. Every view derives from `CViewBase<T>` (`ViewBase.h`), which is built on WTLHelper's `CFrameView`, so each view is a child frame window with its own client area and rebar.
  - Views are heap-allocated and delete themselves when their window is destroyed.
  - Each tab's page data is the view's `CMessageMap*`. `COMMAND_TABVIEW_HANDLER(m_Tabs, 1)`, which comes first in the frame's map, routes `WM_COMMAND` to the active view's `ALT_MSG_MAP(1)`. That section must end with `CHAIN_MSG_MAP_ALT(CViewBase<T>, 1)`.
- **Refresh model:**
  - The frame owns the single `ProcessManager` (`WinSys::ProcessManager<ProcessInfoEx>`, defined in `ProcessInfoEx.h`) and one timer. The interval is the `UpdateInterval` setting, and updates can be paused.
  - On each tick the frame calls `Update()` once, then `IView::OnRefresh(active)` on **every** view. Inactive views update their data but don't redraw.
  - Views get the snapshot through `IMainFrame::GetProcessManager()` and must not take their own.
  - `ProcessInfo::CPU` is in units of 1/10000 of a percent.
- **Font:** Options > Font... saves a `LOGFONT` in the `Font` setting, its height at 96 DPI (no face name: the default; Options > Default Font clears it). The frame creates the font for its DPI (`ApplyFont`; the default is the icon title font, the list views' own) and hands it to every view through `IView::OnFontChanged`, which views apply to their lists and trees (the Processes view also to the lower pane's pages, through `SetListFont`) and the Performance view to its navigation pane and the text below the graphs (the graphs keep their Direct2D fonts). The frame keeps the font until the next change, so a view may hold its handle (the Performance view does, for drive pages added later). With no font set, the frame doesn't call the views at startup, so the controls keep their own fonts. The property sheets keep theirs.
- **Shared image list:** the frame owns the 16×16 image list, which the tab view also uses. Views get it with `GetImageList()`, look up icons with `GetIconIndex(IDI_*)` (`IIconSource`, which `IMainFrame` derives from), and should create their lists with `LVS_SHAREIMAGELISTS`. Register a new icon in `CMainFrame::InitImageList`. Process icons come from `IMainFrame::GetProcessIcon`, which extracts them from the executables and caches them by path (processes without one get the system's application icon).
- **Processes view** (`ProcessesView.*`) uses the standalone TreeListView (`CTreeListViewCtrl`) in callback mode (`TLVN_GETDISPINFO`). Item data is a `ProcessItem*` stored in an `unordered_map`, whose element pointers stay valid. Points to watch:
  - **Filter:** a `CFilterBox` (`FilterBox.*`, shared with the Services view) in the view's own rebar (`CreateSimpleReBar`; the view is a `CFrameWindowImpl`): an edit applied 250 ms after typing stops (a timer on the edit itself), whose `EN_CHANGE` comes to the view through the rebar and is handed back to `Changed`; it calls the view with the lowercase text. A process matches if its image name, PID, user, description or command line contains the text (case-insensitive); `ProcessItem::Match` keeps the result. Every process stays in `m_Items` (deltas, kinds); only matching ones are inserted, and `EnsureInserted` brings their ancestors along (gray when they don't match themselves and have no kind color), so items may have no `Item`. New processes are matched as they appear; Go to Process clears a filter that hides the target. View > Hide Processes, also the Hide drop-down button beside the filter (`m_HideBar`, a one-button toolbar in a second rebar band, checked while an option is on; its menu is that submenu, loaded from `IDR_MAINFRAME`; the view's `UpdateLayout` maximizes its band after every layout, as the rebar gives a row's extra width to the first band, the filter's), hides (`IsHidden`, the `ProcessHide*` settings) other users' processes (no Own kind), services' (the Service kind), Windows processes (the image in the Windows directory, or none: Idle, System, Registry...) and signed ones (a valid signature, verified by a `SignatureVerifier` (`SignatureVerifier.*`, the Kernel Modules view's too: WinSys `FileSignature` on a worker thread, results by path, posting `WM_PROCESS_SIGNED`); shown until verified). A hidden item doesn't match (`ProcessItem::Hidden`), so it's in the tree only as a gray ancestor; as the kinds and the signatures change, `UpdateHidden` puts items into the tree or takes them out (on every refresh, and on `WM_PROCESS_SIGNED`), which is why the kinds are set before items are matched. The status line counts the shown processes while any option is on; Go to Process says so in the status line for a hidden process rather than showing it. Ctrl+F (`ID_EDIT_FIND`) focuses the box; Escape clears it (empty: back to the list), Enter and Down go to the list. The status line's first pane counts the matches. `CMainFrame::PreTranslateMessage` leaves editing keys (Space, Delete, Ctrl+C/V/X/A/Z/Y) to an edit control with the focus, as they're accelerators otherwise.
  - **Removing an item:** `DeleteItem` removes the whole subtree, so `RemoveItem` re-inserts the children first.
  - **Exited processes** are shown for exactly one refresh, then removed. Their `NativeInfo` points into the previous snapshot buffer, and the next `Update()` overwrites it.
  - **Selection:** the inner list view tracks the selection by row index, so after any insert, delete or sort, restore it by item with `SelectItem(h, false)`. An update keeps the scroll position (TreeListView passes `LVSICF_NOSCROLL` whenever it resets the item count, which otherwise scrolls the focused row into view); with View > Keep Selection Visible (the `ProcessKeepSelectionVisible` setting) it scrolls to the selection instead. Rebuilding the list (tree/flat) and a sort from the header always show the selection.
  - **Flat mode** rebuilds the list with every item at the top level, because TreeListView's own flat mode sorts only within each parent.
  - **Image list:** the inner list view has `LVS_SHAREIMAGELISTS` set, since the image list belongs to the frame.
  - **Columns:** `m_Columns` maps list columns to `Column` values; Name is always list column 0, because that column draws the tree, and Name and PID can't be hidden. The display order is the header's order array (the user can also drag columns). Right-clicking the header shows a menu to hide that column or open the dialog; the header's `WM_CONTEXTMENU` reaches the view with the TreeListView as `wParam`, so `OnContextMenu` tells it apart from a row's by the position. View > Select Columns opens `CColumnsDlg` (`ColumnsDlg.*`, a generic check list with a search box, Move Up/Down and Defaults). The shown columns, in display order with their widths, are saved in the `ProcessColumns` setting as `Key:width,...` (keys in `s_Columns`, which must not change), after the dialog and when the view is destroyed. Parsing, saving and running the dialog are shared with the Services view and the lower pane's pages in `ColumnLayout.*` (a table of `ColumnDef`, with `Mandatory` columns that can't be hidden), which also has the helpers for a `CVirtualListView` list whose `ColumnManager` holds only the shown columns: `GetShownColumns`, `SetColumns`, `HeaderColumnAt` (a header's `WM_CONTEXTMENU` is told from a row's by the position) and `PrepareHeaderMenu`. `SetColumns` sets column 0's alignment again after inserting it, because the list view ignores it on insertion.
  - **Lower pane:** the client is a `CCustomHorSplitterWindow` (WTLHelper) with the tree on top and `CProcessDetails` (`ProcessDetails.*`, a `CNativeCustomTabViewImpl` with Handles, Modules and Threads list views) below. View > Lower Pane (Ctrl+L) switches the splitter to single-pane mode; the `ProcessLowerPane` and `ProcessSplitterPos` settings keep it. The splitter forwards the tree's `WM_NOTIFY` to the view. `UpdateDetails` hands the selected process (none for an exited one) to the pane after selection changes and refreshes; `SetProcess` ignores the same process, as the selection is restored on every refresh. Don't give `CProcessDetails` a message map of its own: the tab view's has an `ALT_MSG_MAP(1)` that it routes to, and a map without it asserts. The Threads tab is `CThreadsPage` (`ThreadsPage.*`), a window owning a virtual list view (`CVirtualListView`, sorting by the column manager's tags): each refresh it copies the selected process's threads from the snapshot (the `SYSTEM_EXTENDED_THREAD_INFORMATION` array after the process entry; the frame's `Update()` doesn't build thread objects, which would cost thousands of allocations per tick), and computes CPU and the context switch delta from the previous refresh's values, kept per thread key, over the elapsed QPC time. Ideal CPU, I/O and memory priority and cycles come from a WinSys `Thread` handle per thread (query access, else limited), opened once while the process is shown and kept in the per-thread state; the service (from the TEB's SubProcessTag) is queried once per thread. New threads are highlighted for two refreshes (not on a process's first refresh); a thread that exited is shown once more as a red row from its last values, its state kept for that refresh in `m_Exited` (the row points to its Service string). The selection is restored by thread ID. Its columns work like the Services view's (`ColumnLayout`, the `ThreadColumns` setting, TID mandatory), chosen from the header's context menu only (View > Select Columns belongs to the process list); that menu posts its commands to the page, because a dialog run with `TPM_RETURNCMD` inside the header's right-button handling didn't paint. The Modules tab is `CModulesPage` (`ModulesPage.*`), built the same way on WinSys `ProcessModuleTracker` (one per selected process; it walks the address space, so it's enumerated only while its tab is active, and on activation through `OnPageActivated`): images and mapped data files (page-file-backed sections left out), version strings from `GetCachedVersionInfo` (`VersionInfo.*`, cached per path, also used for the process Description), new modules highlighted for two refreshes and unloaded ones shown for one, columns in the `ModuleColumns` setting; the leftmost column shown has the mapping type's icon from the frame's image list (`IDI_MODULE_IMAGE`, `IDI_MODULE_DATA`; the page gets the frame through `SetFrame`, as the Handles page does). The Handles tab is `CHandlesPage` (`HandlesPage.*`) on WinSys `HandleEnumerator`: the process's own handle snapshot, or the system handle table (about 33 ms for ~360,000 handles) only while the Address column is shown. Names are queried when a row is shown or sorted, through a duplicate of the handle, once per handle: processes and threads by ID and image name (duplicated with query access, so handles without it still show their IDs; the image name from the snapshot, else from the handle), tokens by user and logon session, files as DOS paths, keys as `HKLM\`/`HKCU\`/`HKU\`, the rest by their object names; files through WinSys `ObjectNameQuery` (100 ms timeout; files aren't queried after 4 hung queries), other types directly, as only a file's query can hang. That logic is WinSys `HandleNames::QueryName`, shared with Find Handle or DLL and safe on any thread (with `DosNames`, a drive table of its own, and `RegistryName`); the Memory page uses `DosNames` too for mapped files. WinSys `AccessMaskDecoder` decodes access masks per type. The leftmost column shown (wherever the user drags the columns: `ColumnLayout::IsLeftmostColumn`) has an icon per object type from the frame's image list (`GetHandleIcon`, in `HandleIcons.*`; `IDI_OBJECT` for types without one of their own; files get `IDI_DEVICE` when their name stays an NT name, i.e. devices and pipes; `Dxgk*` types get `IDI_DIRECTX`). The Threads tab's leftmost column likewise shows an icon per thread state (`CThreadsPage::GetRowImage`), from an image list of the page's own, because the page also runs on a property sheet's thread. Highlighting and the `HandleColumns` setting work as in the other pages. Double-clicking a handle, its row menu's Properties or View > Properties (Alt+Enter, routed by `GetKillTarget` while the page has the focus) opens `CHandleSheet` (`HandleSheet.*`), a modal, resizable property sheet with tab icons (WTLHelper `CIconPropertySheetImpl` over `CResizablePropertySheetImpl`) and three tabs; the sheet and the details tab have the type's icon (`GetHandleIcon`), General `IDI_HANDLES`, and Security the system's shield (`IDI_SHIELD`), set in `OnSheetInitialized` because the ACL editor's `HPROPSHEETPAGE` brings no icon the sheet knows. General and the type's details (titled by the type: Mutex, Named Pipe, File...) are `CHandleListPage`s: WinSys `ObjectInspector::QueryHandle` laid out as property lists (`CDialogResize`; bold, shaded section rows on General), where Refresh queries again for both and Copy copies `[Section]` titles and tab-separated properties; a type whose details the handle's access doesn't allow gets a Not Available row. Security is the system's ACL editor page (`CreateSecurityPage`) on a `CObjectSecurityInfo` (`ObjectSecurity.*`) over a duplicate of the handle (`ObjectInspector::OpenHandle`). Apply or OK writes changes made there. The row menu also has Close Handle. Each of the three pages has a filter box above its list (`CFilterBox`, a child of the page; Ctrl+F focuses the filter of the page with the focus, through `CProcessesView::OnFind`): a row matches if any shown column contains the text. A page keeps every row of its last refresh (`m_AllRows`) and shows the matching ones (`ShowRows`, which also sorts and keeps the selection), so a filter change doesn't refresh (the Threads page's deltas and the highlighting go by refreshes). The pages' row menus have Copy (the row's shown columns, tab separated: `ListExport::RowText`); the Modules page's also has Properties (the shell's, `SHObjectProperties`; also on a double-click) and Open File Location. Each page is refreshed only while its tab is active, and when it's activated (the Threads page's deltas cover the time since its last refresh); the pane does nothing while hidden, and a selection change reaches it after 150 ms (`DetailsTimerId`), so keyboard navigation doesn't enumerate every process it passes.
  - **Row colors** (`ProcessColors.*`): each `ProcessItem` keeps its `ProcessKind` flags, worked out at refresh time so `OnCustomDraw` only looks up the table: Secure, Protected (WinSys `Process::IsSecure`/`IsProtected`, cached in `ProcessInfoEx`), Immersive, Job and Own (the user is the app's own entry's, `GetUser`, so the formats match) when the item is added; Suspended on every refresh (every thread Waiting for Suspended or WrSuspended, as a suspended process's or a frozen Store app's); Service from the PIDs of active services (`EnumServices`, done again on the update when processes start and the next one, since a service host is a new process); .NET from WinSys `DotNetInfo`: the `dotnet-diagnostic-<pid>` pipes (.NET Core and later, `GetCoreRuntimeProcesses`) or the CLR's `Cor_Private_IPCBlock[_v4]_<pid>` section in the process's session (.NET Framework, `HasFrameworkRuntime`), checked again on every update while a process is younger than 15 s, because the runtime starts after the process. The exited and new highlights are kinds too (`Exited`, `New`, added in `OnCustomDraw`), so the first enabled kind in `ProcessColors::Defaults` order (Exited, New, Suspended, Secure, Protected, Immersive, .NET, Services, Jobs, Own) gives the color, light or dark. The `ProcessColors` setting holds `Key:enabled:RRGGBB:RRGGBB` per kind (keys must not change); Options > Process Colors... opens `CProcessColorsDlg` (`ProcessColorsDlg.*`): a check box per kind to use its color (Jobs off by default) and owner-drawn swatches for the light and dark colors that open the color dialog, and a Default button per row that restores its colors (not its check box), enabled while they differ from the defaults; the template's `IDC_PCOLOR_*` ranges (blocks of ten IDs, one per kind) follow the `Defaults` order, so a new kind needs a row in the template and the ranges renumbered. After OK the frame saves the setting and tells the views through `IView::OnProcessColorsChanged`.
  - **Process commands:** the Process menu (after View) and the row context menu both hold Kill, Kill Process Tree (the root first, then its descendants from the snapshot by parent ID and creation time, the app's own process left out), Kill All with the Same Name (by image name, case-insensitive), Restart (WinSys `Process::Restart`: the image, command line, current directory and environment read, the process terminated and created again by the app, with its account and elevation; not for services' processes, packaged apps or the app itself), Suspend, Resume, Set Priority and Open File Location; `UpdateUI` enables the menu's items (and checks the priority) for the selected process, on selection changes and refreshes, and disables them while another tab is active.
 The toolbar's Kill button and Del are `ID_KILL`, which acts on the list with the focus (`GetKillTarget`): the process tree kills the process (as `ID_PROCESS_KILL`, which the Process menu keeps), the lower pane's Threads page terminates the thread (`CThreadsPage::TerminateSelected`, the context menu's command), its Handles page closes the handle in its process (`CHandlesPage::CloseSelected`: WinSys `HandleNames::CloseInProcess` after a confirmation, which closes it only if the value still refers to an object of the row's type; not the app's own handles), and the Modules page does nothing. The focus changes without the view being told, so the frame calls the active view's `IView::OnFrameIdle` from its idle handler, where the view enables `ID_KILL` (`OnIdle` is taken: `CViewBase`'s idle handler). Its toolbar tooltip says what it would do (Kill Process, Terminate Thread, Close Handle): the frame answers `TTN_GETDISPINFO` for `ID_KILL` itself with the active view's `IView::GetCommandTip`, never with `TTF_DI_SETITEM` (which `CFrameWindowImpl`'s handler sets, making the tooltip keep the text). Create Dump (Minidump, Full Dump) asks for a file (`name_pid_date_time.dmp`) and writes it with WinSys `MiniDump::Write` on the symbol engine's thread (`SymbolEngine::WriteDump`; DbgHelp isn't thread-safe), which posts `WM_DUMP_WRITTEN` to the view; a minidump has threads, modules, handles and memory info, a full dump all the memory. The menus also set, through a WinSys `Process` opened with `SetInformation` (`OpenSelected`), the I/O priority (`SetIoPriority`), the memory priority (`SetMemoryPriority`), the affinity (`CAffinityDlg`, `AffinityDlg.*`: a check box per processor, laid out at run time in rows of eight, all created in `WM_INITDIALOG`, as the theming reaches only the windows there are then; with more than one processor group (over 64 processors, WinSys `SystemInfo::GetProcessorGroups`) a combo box shows one group at a time, each keeping its selection, processors numbered across the groups. `SetGroupsAffinity` then sets a process held to one group by an affinity mask (`GetAffinity` succeeds) by that mask, its other groups shown disabled, and any other process (spanning the groups, which has no single mask) by its default CPU sets, `SetDefaultCpuSetMasks`, every processor clearing them) Reduce Working Set (`Process::EmptyWorkingSet`), Critical Process (checked for a critical process, `Process::IsCritical`; enabled only when elevated, as `Process::SetCritical` needs SeDebugPrivilege; a confirmation either way: Windows crashes when a critical process exits; protected processes can't be opened for it), Debug (`Process::AttachDebugger`: the AeDebug key's Debugger command line with the PID, without its crash-only arguments, after a confirmation that shows it) and Efficiency Mode (`SetEfficiencyMode`, as Task Manager: EcoQoS plus the Idle class; off: the system decides again, at Normal), with the current values checked (`ProcessInfoEx::GetEfficiencyMode`, the priorities through its handle).
  - **Process properties** (`ProcessSheet.*`, `ProcessPages.*`): double-clicking a process, View > Properties (Alt+Enter) or the context menu's Properties opens `CProcessSheet`, a modeless WTLHelper `CIconPropertySheetImpl` over `CResizablePropertySheetImpl` (tab icons, resizable, a Close button only), on a thread of its own with its own message loop (`ShowProcessProperties`). It has no owner and its own taskbar button. The sheet gets a `ProcessProperties` copy made on the UI thread, never the snapshot (the frame's `ProcessManager` isn't thread-safe); pages query anything else from the process themselves. WTLHelper's theming hook is per thread, so the sheet's thread installs it with `WTLHelper::InitThread` (and removes it with `TermThread`); only the sheet's title bar is set by hand. The General page lays out its controls with WTL's `CDynamicDialogLayout`, from the `AFX_DIALOG_LAYOUT` resource of `IDD_PROC_GENERAL` in `WinSysLive.rc`: four percentages (move X/Y, size X/Y) per control, in the template's order, so a control added to the template needs its row there too. Pages: General (implemented: identity, the ASLR/CFG/CET/DEP mitigation policies (`GetProcessMitigationPolicy`, plus the image header's DYNAMIC_BASE and HIGH_ENTROPY_VA for ASLR), signature verification on demand (WinSys `FileSignature::Verify`: WinVerifyTrust on the embedded signature, else the system catalog that lists the file's hash; no revocation checks; `Signature.*` words the result) and Kill, which checks the process's start time so a reused PID isn't killed) Statistics (`CProcStatsPage`, `StatisticsPage.*`, after Performance: every counter in one owner-data list, in sections drawn bold and shaded as the handle sheet's (CPU: priority, times, cycles, context switches, threads; Memory: private bytes, virtual size, working set, page faults, pools, each with its peak, memory priority; I/O: operations and bytes by type, I/O priority; Handles and Objects: handles, GDI and USER objects with their peaks), from the sheet's snapshot and, for the peaks of handles (WinSys `Process::GetPeakHandleCount`) and GUI objects and the priorities, a limited-access handle opened once; fed every sample while active, the Change column against the previous sample shown (starting over when activated); Copy and Copy All) Environment (`CProcEnvironmentPage`: a `CVirtualListView` of the variables from WinSys `Process::GetEnvironment`, read when the page is first shown; Copy and Copy All put `NAME=value` lines on the clipboard; it uses no `WS_EX_COMPOSITED`, which slows list views), Token (`CProcTokenPage`, filled once (its Security... button opens the token's own permissions, `EditSecurity` on a `CObjectSecurityInfo`, the token opened with the most of READ_CONTROL, WRITE_DAC and WRITE_OWNER it allows): the token's properties from WinSys `Token` and `LsaSecurity::GetLogonSessionData` in read-only edits, grouped in Identity, Logon, Token and Security boxes in one column on the left, and on the right two plain report lists, one above the other: its privileges with their descriptions (each with `IDI_ENABLED` or `IDI_DISABLED`, from an image list of the page's own, as it runs on the sheet's thread, rebuilt on `WM_DPICHANGED_AFTERPARENT`), and its groups followed by an AppContainer's capabilities, in the token's order until the Privilege or Name header is clicked (those columns sort, case-insensitively, a click again reversing it; Close Handles closes the row's handles in the holder and Close All Handles every handle to the zombie (`HandleNames::CloseInProcess`, type Process, after a confirmation); double-click or Go to Holder calls `GoToProcess`. Columns as in the other list tabs (`ColumnLayout`, the `ZombieColumns` setting, Zombie mandatory).
- **Object Types view** (`ObjectTypesView.*`, the tenth tab, Ctrl+0, `IDI_OBJECT`), as ObjectExplorer's: the kernel's object types from WinSys `ObjectTypes::Enum` (one `ObjectTypesInformation` query) with their counts and peaks, pool type and default charges, valid access mask, generic mapping (decoded by `AccessMaskDecoder`) and invalid attributes. Read on every tick, also while hidden; a count that changed since the previous refresh has its cell colored for that refresh (`Row::Change`, subitem custom draw: green up, red down; the other cells get back the colors the list chose for the row at the item stage, never `CLR_DEFAULT`, which is the system's black text even on a dark selection). The icons are the Handles page's (`GetHandleIcon`). The filter matches the name; columns as in the other list tabs (`ObjectTypeColumns`, Name mandatory).
- **Wait chains** (`WaitChainDlg.*`): Wait Chain... in the Threads pages' row menu (one thread) and Analyze Wait Chain... in the Process menus (every thread of the process, from the snapshot) open `CWaitChainDlg`, modal, filled from a `std::jthread` (WinSys `WaitChainTraversal::GetThreadWaitChain` per thread, which can wait on hung processes) that posts `WM_WAITCHAINS_READ`. A chain's nodes are rows indented by depth (thread, the object it waits for, the thread owning that...); deadlocked chains (WCT's cycle) come first and are red, then the chains through other threads; a node WCT knows only by process (out-of-process COM, a process wait) shows the process. The wait time shows only for blocked threads. Refresh reads again; Copy copies the rows.
- **Export** (`ListExport.*`): File > Export List (Ctrl+S) saves, and Copy All Rows (Ctrl+Shift+C) copies, a list view of the active view's that has the focus (the lower pane's pages too), else the view's `IView::GetExportList`: the shown columns in display order and every row, read with `LVM_GETITEMTEXT` (owner-data and callback lists answer as they would to paint). A TreeListView leaves column 0's text out of its inner list (it draws that column itself), so views with one answer `IView::GetTreeColumnText` from `CTreeListViewCtrl::GetCellText` and `GetVisibleItem`. CSV (RFC 4180 quoting) or tab-separated text, UTF-8 with a BOM.
- **ACL editor** (`ObjectSecurity.*`): `CObjectSecurityInfo` is the `ISecurityInformation` the handle sheet, the process sheet's Security page and the Token page's Security... button give the system's ACL editor: an object's descriptor through WinSys `ObjectInspector::GetSecurity`/`SetSecurity`, read-only without WRITE_DAC in the handle's access and the owner without WRITE_OWNER (`Open` tries READ_CONTROL with both, with WRITE_DAC, then alone); the rights it lists are the type's (`AccessMaskDecoder::GetSpecificRights`) and the standard ones, mapped through the type's generic mapping (`ObjectInspector::QueryTypeStatistics`). `SetSecurityTabIcon` puts the system's shield on the editor page's tab. `CAclDialogTheming`, a member of each sheet installed once it exists, gives the editor's own dialogs (Advanced, a permission entry, Select User or Group, `EditSecurity`'s sheet) dark title bars: a CBT hook on the thread applies `WTLHelper::ApplyMode` to each window the sheet owns (directly or through such a dialog) from a zero-delay thread timer after its first activation, as a dialog builds its contents after it's activated. The Advanced dialog is DirectUI: its buttons, tab and edges stay light in dark mode (suspending WTLHelper's hook didn't make it consistent: the detoured system colors keep its background dark).
- **Tray and window options** (Options menu, `TrayIcon.*`): Tray Icon (the `TrayIcon` setting, on by default) shows `CTrayIcon`, a CPU history graph drawn on every refresh (one column per sample, from the status bar's CPU value) with CPU and memory in its tooltip; it's added again on `TaskbarCreated` (Explorer restarted). A left click brings the window back; the right-click menu has Show/Hide, Pause Updates, Always on Top and Exit. Minimize to Tray (`MinimizeToTray`) hides the window when it's minimized (`WM_SIZE`), only while the icon is shown, and turning the icon off brings a hidden window back. Always on Top (`AlwaysOnTop`) is `HWND_TOPMOST`. Single Instance (`SingleInstance`, off by default): starting the app again brings the running instance to the front, as below, and exits; `ActivateRunningInstance` runs after the settings are loaded, and Run as Administrator passes `/restart`, which skips it, as the elevated instance starts while this one still runs. Replace Task Manager (enabled only when elevated) writes or deletes the `Debugger` value of `taskmgr.exe`'s Image File Execution Options in HKLM; it's checked when that value names this exe (Process Explorer's doesn't count). Windows then starts the app with taskmgr.exe's path as an argument, so `ActivateRunningInstance` in `WinSysLive.cpp` posts `CMainFrame::ActivateMessage` (registered) to a running instance (found by the frame's fixed class name, `WinSysLiveFrame`) and exits; that message and `TaskbarCreated` are let through UIPI (`ChangeWindowMessageFilterEx`), since the running instance may be elevated.
- **Performance view** (`PerfView.*`, `PerfNav.*`, `PerfPages.*`): a list of pages on the left (`CPerfNav`, a custom-drawn window with a small history graph for each resource, which scrolls when the items don't fit; Up, Down, Page Up, Page Down, Home and End move the selection) and the selected page on the right. Summary shows CPU, memory, network and total disk transfer, in a 2×2 grid when the page is wide enough. The selected page is saved by name in the `PerfPageKey` setting (`PageKey`: "CPU", "Disk:C", "GPU:0"...), as the drive and GPU pages' indices shift when drives come and go; the older `PerfPage` index is read only when there's no name yet.
  - `CPerfView` takes one `PerfSample` per refresh tick from WinSys `SystemInfo` (per-processor times queried for each processor group, plus performance, basic and memory list information) and hands it to **every** page, also hidden ones, so their graphs have history when shown.
  - Pages implement `IPerfPage` through the `CPerfPage<T>` base (background, text lines below the graphs, layout): Summary, CPU, Memory, Network, I/O (`CPerfIoPage`: the system's read, write and other transfer rates and operations per second, all processes' I/O, from `SYSTEM_PERFORMANCE_INFORMATION`'s counters, which `CPerfView::SampleIo` turns into rates over QPC time; its key is "IO"), one per drive, one per GPU and one per NPU. To add one, add the data to `PerfSample`, write the page class, and add a nav item and a `m_Pages` entry in the same order (`NavItem`).
  - Graphs are GraphControl's `CGraphControl`, `CGraphGrid` and `CCompositionBar` from wtlhelper, included as `<GraphControl/include/...>`. Each graph keeps its own history, so a graph shown on two pages is two controls fed the same sample.
  - Network data comes from WinSys `NetworkTracker` (`<WinSys/Network.h>`, `GetIfTable2`, about 4 ms per tick), owned by the view; the sample points to its interface list. The Network page graphs only adapters that are up, and creates or destroys their graphs as that set changes.
  - Drive pages come from WinSys `DiskTracker` (`<WinSys/Disk.h>`). They're dynamic: `SyncDiskPages` inserts and removes pages and nav items, in drive letter order from `FirstDiskItem`, when drives appear or disappear. That's why the view keeps `m_Theme` and `m_TimeSpanText`, which pages created later need.
  - GPU pages (`CPerfGpuPage`) come from WinSys `Gpu.h`: `GpuInfo::GetAdapters` reads the adapters once (`D3DKMTEnumAdapters2`, software and non-rendering ones left out, names from DXGI, engine names from `KMTQAITYPE_NODEMETADATA`, grouped by name; aperture segments are shared memory), and `GpuTracker` samples the nodes' running times (100 ns units, whatever the header says) and the segments' resident bytes. An engine's utilization is its busiest node's, an adapter's its busiest engine's (as Task Manager). The pages follow the drive pages (`FirstGpuItem`), so they move as drives come and go; each has a grid of engine graphs and the dedicated and shared memory graphs.
  - NPU pages are GPU pages (`CPerfGpuPage` with `GpuAdapterKind::Npu`, their adapters and samples from a second `GpuTracker`), after the GPU pages (`FirstNpuItem`, keys "NPU:0"...).
  - All pages are kept sized, not just the visible one, because laying out the per-processor grid is slow. The CPU page sets the grid's layout from its aspect ratio, because the grid's automatic layout is square.
  - The CPU page's Show processors check box (at the end of the text block; the `PerfShowProcessors` setting) hides the per-processor grid, the CPU graph then taking its place; hidden, the grid still takes the samples. Child controls on a page must have the page's background drawn under them: WTLHelper's dark mode paints a check box with `DrawThemeParentBackground`, whose `WM_ERASEBKGND` the pages leave undone (they fill in `WM_PAINT`), so the CPU page fills an erase request for another window's DC itself (`WindowFromDC`), and answers `WM_PRINTCLIENT` and the `WM_CTLCOLOR*` messages in the graph theme's colors.
- **Symbols** (`Symbols.*`, `SymbolEngine`): DbgHelp, which isn't thread-safe, is called (through WinSys `SymbolHandler` and `MiniDump`) only on the engine's own thread; `Lookup` and `CaptureStack` may be called from any thread (the UI's, the property sheets') and answer with `WM_SYMBOLS_RESOLVED` (the window repaints; the next `Lookup` finds the cached text) and `WM_STACK_CAPTURED` (lParam: a `StackCapture*` the window owns). The engine loads the exe folder's `dbghelp.dll` before the first call (then `SymbolHandler::SetOptions`) (delay-loaded, so the copy beside `symsrv.dll` is the one used; the system's can't download). The search path comes from Options > Symbol Settings... (`CSymbolSettingsDlg`, `SymbolSettingsDlg.*`, after TotalPE's: the `Symbol*` settings as `SymbolPathOptions`), built by `BuildSymbolSearchPath` on the UI thread (the settings belong to it) and handed to the engine with `SetSearchPath` at startup and after the dialog: the extra paths, then `_NT_SYMBOL_PATH` (with `cache*` the cache added if it has a server but no cache), then `srv*`(cache)`*`(server) unless `_NT_SYMBOL_PATH` has a server; an empty cache is TotalPE's (its `SymbolCache` setting, else `%LOCALAPPDATA%\TotalPE\Symbols`). A new path closes the engine's sessions and clears its cache, so addresses resolve again with it. A process's session is a `SymbolHandler::ForProcess` (up to 16, the least recently used closed); kernel addresses use one `SymbolHandler::ForKernel`, whose module bases only an elevated process gets (tried once per search path). Resolved text is cached by process (ID and creation time) and address. A stack is captured by `SymbolHandler::CaptureStack` (the thread suspended only to copy its context and stack; the walk reads that copy, so no symbol download happens with a thread suspended), then resolved by the engine. WinSysLive's own threads are never suspended. Options > Resolve Symbols (the `ResolveSymbols` setting, on by default) turns `Lookup` off (the addresses show) and leaves stack frames without symbols. The Threads pages (lower pane and sheet) show the start address's symbol in Start Address, with the address in a tooltip (a tooltip for the whole list, popped when the mouse moves to another cell, as the list view's infotips are only for the first column), and open `CStackDlg` (`StackDlg.*`) from a row's context menu or a double-click: modal, filled when the capture arrives, with Refresh and Copy. Each frame shows its module and where its symbols came from (WinSys `SymbolHandler::GetModuleSymbols`, after resolving: the PDB's path, exports only, none, or not loaded while Resolve Symbols is off), the status line names the modules without a PDB, and double-clicking a frame opens its module's folder with the file selected. The row's context menu also has Set Priority (the seven levels, the current one checked from the page's handle; `ID_THREAD_PRIORITY_*`, in the menu's order) and Affinity... (`CAffinityDlg` with the thread's group, its label speaking of the thread; with several groups, every group is offered, a thread's processors in one of them, as choosing in another clears the rest, and another group moves the thread there, `Thread::SetGroupAffinity`, unless its process is held to its group by a mask), without confirmation, through `CThreadsPage::OpenRowThread`, and Suspend or Resume (by the snapshot: Waiting with a Suspended or WrSuspended wait reason) and Terminate, each after a confirmation, on a WinSys `Thread` opened with only the access it needs and checked against the row's creation time (`GetCreateTime`; a reused thread ID); they're grayed for the app's own threads (suspending one could hang it) and the Idle and System processes'. The new state shows with the next refresh. The menu's icons (`IDI_STACK`, `IDI_PAUSE`, `IDI_RUN`, `IDI_DELETE`) are set with `WTLHelper::InitMenu`, as the frame's are; it's thread-safe, so the sheets' pages use it too.
- **DPI** (per-monitor v2, from `WinSysLive.manifest`: the project's own DPI setting gives only v1, whose child windows get no `WM_DPICHANGED_AFTERPARENT`; `_WTL_DPI_SUPPORT` in `pch.h` for `CDialogResize`). Sizes are written at 96 DPI and scaled to the window's (`DpiHelper` from WTLHelper):
  - **Columns:** `ColumnManager::AddColumn` scales its width, so `ColumnLayout` and the views pass and save widths at 96 DPI (`GetShownColumns` scales them back); the TreeListViews (Processes, Users, Memory) scale their own and get `ListViewHelper::EnableColumnDpiScaling` on the inner list, as do lists with columns inserted directly. That subclass, the filter box's and the pages' all rely on `WM_DPICHANGED_AFTERPARENT`, which WTLHelper's dark mode subclasses used to swallow (see `wtlhelper/CLAUDE.md`).
  - **Frame:** `WM_DPICHANGED` takes the suggested rectangle, rebuilds the shared image list in place (`UpdateImageList`: `SetIconSize`, the same handle and indices, process icons extracted again with `SHDefExtractIcon` at the new size), the toolbar's images and band (`UpdateToolBar`), the menu icons (`WTLHelper::InitMenu` takes an icon size; context menus pass `DpiHelper::SmallIconSize`), the status bar panes and a user font (`ApplyFont`), then calls `IView::OnDpiChanged` on every view, which gives its lists the image list again so their rows take its height. The window's placement is saved with its DPI (`MainWindowPlacementDpi`) and `Run` restores the size for the monitor's DPI.
  - **Filter box:** its width is at 96 DPI; it follows its DPI by itself (own font unless the view gave one, size, rebar band, or the parent's layout through a `WM_SIZE`).
  - **Dialogs** (`DpiLayout.h`): the property pages are child dialogs, which get `WM_DPICHANGED_AFTERPARENT` and which the dialog manager would relayout by the new font's dialog units, not the DPI ratio WTL's layouts scale by (rows came apart). So it only scales their fonts (`DDC_DISABLE_CONTROL_RELAYOUT`), and `CDpiDynamicDialogLayout` (for `CDynamicDialogLayout` pages) or `CDpiDialogResizePage` (`CDialogResize`) moves every control by the ratio and lays the page out again. Top-level dialogs with `CDialogResize` chain `CDpiDialogResize`: WTL's handler doesn't take the suggested size. A page or dialog calls `InitDpi` after `DlgResize_Init` (the dynamic layout's `InitDynamicLayout` does it itself).
  - The Threads page and the Wait Chain dialog have image lists of their own in the window's small icon size (the page rebuilds its on a DPI change); the tray icon stays at the system DPI.
- **Painting performance:** WTLHelper installs a thread-wide `WH_CALLWNDPROCRET` hook to theme new windows. While it's installed, every `SendMessage` goes through the kernel, and that roughly doubled the time to repaint the process list. For any list with many rows or callbacks, call `SuspendHookWhilePainting(hList)` from `ViewBase.h`; it removes the hook during `WM_PAINT` (`WTLHelper::SuspendHook` really unhooks). Measured per refresh tick with the Processes tab visible: ~20 ms for the snapshot (on the UI thread) and ~60 ms for painting.
- **Adding a tab** takes four steps:
  1. Add a value to `TabType` (`Interfaces.h`).
  2. Write `XxxView.h/.cpp`.
  3. Add a `case` to `CMainFrame::CreateView` (`ViewFactory.cpp`).
  4. Add an entry to `CMainFrame::s_Tabs` (with a key for the `Tabs` setting), an `ID_VIEW_*` command (View menu item and Ctrl+N accelerator), its toolbar button in `s_ToolBarButtons` (`BTNS_CHECK`) and a `COMMAND_ID_HANDLER(ID_VIEW_*, OnViewTab)` in the frame's message map.

## Conventions

- Every `.cpp` starts with `#include "pch.h"` (ATL/WTL and STL headers live there).
- Classes use WTL style: `C` prefix, `m_` members, message maps with the commented handler-prototype boilerplate, tabs for indentation, and opening braces on the same line.
- New command IDs go in `resource.h` and the menu in `WinSysLive.rc`. When adding a source file, register it in both `WinSysLive.vcxproj` and `WinSysLive.vcxproj.filters`.
