# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

WinSysLive is a native Win32 GUI app (C++23, ATL/WTL, Unicode) at an early stage: a WTL frame window hosting a tabbed view. The app code lives in `WinSysLive/`; the heavy lifting comes from two git submodules by the same author, each with its own `CLAUDE.md` to read before changing it:

- `wtlhelper/`: WTL UI libraries. `WTLHelper` (static lib: dark mode, `Settings`, list-view/tab helpers, vendored WTL headers in `WTL/`) and `GraphControl` (Direct2D time-series graph) are both projects in `WinSysLive.sln`.
- `winsys/`: the `WinSys` static library (NT native API wrappers: processes, threads, `ProcessManager<>` snapshots, services, network interface and drive statistics, and so on). The app references it, along with WTLHelper, TreeListView, GraphControl and HexControl (`<HexControl/SimpleHexControl.h>`, a static lib in `wtlhelper/HexControl`).

If the submodule directories are empty, run `git submodule update --init`.

## Build

MSBuild only. There is no CMake, lint, or test setup for the app itself. Toolset v145 (VS 18).

```powershell
msbuild WinSysLive.sln /p:Configuration=Debug /p:Platform=x64 /m
msbuild WinSysLive\WinSysLive.vcxproj /p:Configuration=Debug /p:Platform=x64   # app + WTLHelper (project reference)
```

Dependencies come from the submodules. WTLHelper needs its NuGet packages (Detours, WIL, wtl), restored with `nuget restore wtlhelper\WTLHelper.sln`. WinSys needs phnt and WIL from vcpkg (user-wide integration) and must stay pinned to Windows SDK `10.0.26100.0` (see `winsys/CLAUDE.md` for why).

Include paths are `..\wtlhelper\WTLHelper` and `..\wtlhelper\WTL` (WTLHelper headers such as `WTLHelper.h`, `Settings.h` and `NativeCustomTabView.h` are included by bare name), plus `..\wtlhelper` and `..\winsys` so that the other libraries are included with a folder prefix: `<WinSys/ProcessManager.h>`, `<TreeListView/include/TreeListView.h>`. Keep that prefix. WinSys and WTLHelper both have a `SecurityHelper.h`, and WTLHelper has its own, different `TreeListView.h`. The CRT is linked statically (`MultiThreaded[Debug]`).

The include order in `pch.h` matters, and the reasons are commented there:
1. Full `windows.h` first (with `WIN32_NO_STATUS`), because `phnt_windows.h` forces `WIN32_LEAN_AND_MEAN`.
2. `phnt_windows.h`, then `#undef INITGUID`.
3. ATL/WTL.
4. `phnt.h` last, because it `#define`s `TOKEN_INFORMATION_CLASS` values that break `atlcom.h`.

`NOMINMAX` is defined at the top of `pch.h`; phnt would define it, but too late now that `windows.h` comes first.

## Architecture

- `WinSysLive.cpp`: `_tWinMain` initializes COM and `CAppModule _Module`, loads settings from the registry key `Software\ScorpioSoftware\WinSysLive`, calls `WTLHelper::InitDarkMode(...)` *before* any window is created, then runs the message loop with a single `CMainFrame`.
- `AppSettings.h`: a `Settings` subclass declared with WTLHelper's `BEGIN_SETTINGS`/`SETTING`/`DEF_SETTING` macros. The first constructed instance becomes the singleton (the global `AppSettings _Settings` in `WinSysLive.cpp`) and is reached anywhere through `AppSettings::Get()`. To add a persisted option, add a `SETTING(...)` entry plus a `DEF_SETTING(...)` accessor, and call `Save()` after changing it.
- `MainFrm.*`: `CMainFrame` (`CFrameWindowImpl` + `CAutoUpdateUI`, and it implements `IMainFrame`) hosts fixed tabs in `CMainTabView`, a `CNativeCustomTabViewImpl` with the close button turned off. Dark mode is toggled through `WTLHelper::SwitchToMode`, after which every thread window is redrawn and the status bar background is set by hand.
- Views follow TotalPE (`C:\dev\totalpe2\totalpe`):
  - `Interfaces.h` declares `IMainFrame` and `IView`. Every view derives from `CViewBase<T>` (`ViewBase.h`), which is built on WTLHelper's `CFrameView`, so each view is a child frame window with its own client area and rebar.
  - Views are heap-allocated and delete themselves when their window is destroyed.
  - Each tab's page data is the view's `CMessageMap*`. `COMMAND_TABVIEW_HANDLER(m_Tabs, 1)`, which comes first in the frame's map, routes `WM_COMMAND` to the active view's `ALT_MSG_MAP(1)`. That section must end with `CHAIN_MSG_MAP_ALT(CViewBase<T>, 1)`.
- **Refresh model:**
  - The frame owns the single `ProcessManager` (`WinSys::ProcessManager<ProcessInfoEx>`, defined in `ProcessInfoEx.h`) and one timer. The interval is the `UpdateInterval` setting, and updates can be paused.
  - On each tick the frame calls `Update()` once, then `IView::OnRefresh(active)` on **every** view. Inactive views update their data but don't redraw.
  - Views get the snapshot through `IMainFrame::GetProcessManager()` and must not take their own.
  - `ProcessInfo::CPU` is in units of 1/10000 of a percent.
- **Font:** Options > Font... saves a `LOGFONT` in the `Font` setting, its height at 96 DPI (no face name: the default; Options > Default Font clears it). The frame creates the font for its DPI (`ApplyFont`; the default is the icon title font, the list views' own) and hands it to every view through `IView::OnFontChanged`, which views apply to their lists and trees (the Processes view also to the lower pane's pages, through `SetListFont`) and the Performance view to its navigation pane and the text below the graphs (the graphs keep their Direct2D fonts). The frame keeps the font until the next change, so a view may hold its handle (the Performance view does, for drive pages added later). With no font set, the frame doesn't call the views at startup, so the controls keep their own fonts. The property sheets keep theirs.
- **Shared image list:** the frame owns the 16×16 image list, which the tab view also uses. Views get it with `GetImageList()`, look up icons with `GetIconIndex(IDI_*)`, and should create their lists with `LVS_SHAREIMAGELISTS`. Register a new icon in `CMainFrame::InitImageList`. Process icons come from `IMainFrame::GetProcessIcon`, which extracts them from the executables and caches them by path (processes without one get the system's application icon).
- **Processes view** (`ProcessesView.*`) uses the standalone TreeListView (`CTreeListViewCtrl`) in callback mode (`TLVN_GETDISPINFO`). Item data is a `ProcessItem*` stored in an `unordered_map`, whose element pointers stay valid. Points to watch:
  - **Removing an item:** `DeleteItem` removes the whole subtree, so `RemoveItem` re-inserts the children first.
  - **Exited processes** are shown for exactly one refresh, then removed. Their `NativeInfo` points into the previous snapshot buffer, and the next `Update()` overwrites it.
  - **Selection:** the inner list view tracks the selection by row index, so after any insert, delete or sort, restore it by item with `SelectItem(h, false)`. An update keeps the scroll position (TreeListView passes `LVSICF_NOSCROLL` whenever it resets the item count, which otherwise scrolls the focused row into view); with View > Keep Selection Visible (the `ProcessKeepSelectionVisible` setting) it scrolls to the selection instead. Rebuilding the list (tree/flat) and a sort from the header always show the selection.
  - **Flat mode** rebuilds the list with every item at the top level, because TreeListView's own flat mode sorts only within each parent.
  - **Image list:** the inner list view has `LVS_SHAREIMAGELISTS` set, since the image list belongs to the frame.
  - **Columns:** `m_Columns` maps list columns to `Column` values; Name is always list column 0, because that column draws the tree, and Name and PID can't be hidden. The display order is the header's order array (the user can also drag columns). Right-clicking the header shows a menu to hide that column or open the dialog; the header's `WM_CONTEXTMENU` reaches the view with the TreeListView as `wParam`, so `OnContextMenu` tells it apart from a row's by the position. View > Select Columns opens `CColumnsDlg` (`ColumnsDlg.*`, a generic check list with a search box, Move Up/Down and Defaults). The shown columns, in display order with their widths, are saved in the `ProcessColumns` setting as `Key:width,...` (keys in `s_Columns`, which must not change), after the dialog and when the view is destroyed. Parsing, saving and running the dialog are shared with the Services view and the lower pane's pages in `ColumnLayout.*` (a table of `ColumnDef`, with `Mandatory` columns that can't be hidden), which also has the helpers for a `CVirtualListView` list whose `ColumnManager` holds only the shown columns: `GetShownColumns`, `SetColumns`, `HeaderColumnAt` (a header's `WM_CONTEXTMENU` is told from a row's by the position) and `PrepareHeaderMenu`. `SetColumns` sets column 0's alignment again after inserting it, because the list view ignores it on insertion.
  - **Lower pane:** the client is a `CCustomHorSplitterWindow` (WTLHelper) with the tree on top and `CProcessDetails` (`ProcessDetails.*`, a `CNativeCustomTabViewImpl` with Handles, Modules and Threads list views) below. View > Lower Pane (Ctrl+L) switches the splitter to single-pane mode; the `ProcessLowerPane` and `ProcessSplitterPos` settings keep it. The splitter forwards the tree's `WM_NOTIFY` to the view. `UpdateDetails` hands the selected process (none for an exited one) to the pane after selection changes and refreshes; `SetProcess` ignores the same process, as the selection is restored on every refresh. Don't give `CProcessDetails` a message map of its own: the tab view's has an `ALT_MSG_MAP(1)` that it routes to, and a map without it asserts. The Threads tab is `CThreadsPage` (`ThreadsPage.*`), a window owning a virtual list view (`CVirtualListView`, sorting by the column manager's tags): each refresh it copies the selected process's threads from the snapshot (the `SYSTEM_EXTENDED_THREAD_INFORMATION` array after the process entry; the frame's `Update()` doesn't build thread objects, which would cost thousands of allocations per tick), and computes CPU and the context switch delta from the previous refresh's values, kept per thread key, over the elapsed QPC time. Ideal CPU, I/O and memory priority and cycles come from a WinSys `Thread` handle per thread (query access, else limited), opened once while the process is shown and kept in the per-thread state; the service (from the TEB's SubProcessTag) is queried once per thread. New threads are highlighted for two refreshes (not on a process's first refresh); a thread that exited is shown once more as a red row from its last values, its state kept for that refresh in `m_Exited` (the row points to its Service string). The selection is restored by thread ID. Its columns work like the Services view's (`ColumnLayout`, the `ThreadColumns` setting, TID mandatory), chosen from the header's context menu only (View > Select Columns belongs to the process list); that menu posts its commands to the page, because a dialog run with `TPM_RETURNCMD` inside the header's right-button handling didn't paint. The Modules tab is `CModulesPage` (`ModulesPage.*`), built the same way on WinSys `ProcessModuleTracker` (one per selected process; it walks the address space, so it's enumerated only while its tab is active, and on activation through `OnPageActivated`): images and mapped data files (page-file-backed sections left out), version strings from `GetCachedVersionInfo` (`VersionInfo.*`, cached per path, also used for the process Description), new modules highlighted for two refreshes and unloaded ones shown for one, columns in the `ModuleColumns` setting. The Handles tab is `CHandlesPage` (`HandlesPage.*`) on WinSys `HandleEnumerator`: the process's own handle snapshot, or the system handle table (about 33 ms for ~360,000 handles) only while the Address column is shown. Names are queried when a row is shown or sorted, through a duplicate of the handle, once per handle: processes and threads by ID and image name (duplicated with query access, so handles without it still show their IDs; the image name from the snapshot, else from the handle), tokens by user and logon session, files as DOS paths, keys as `HKLM\`/`HKCU\`/`HKU\`, the rest the object name through WinSys `ObjectNameQuery` (100 ms timeout; files aren't queried after 4 hung queries). `AccessMask.*` decodes access masks per type. The leftmost column shown (wherever the user drags the columns: `ColumnLayout::IsLeftmostColumn`) has an icon per object type from the frame's image list (`GetTypeIcon`; `IDI_OBJECT` for types without one of their own; files get `IDI_DEVICE` when their name stays an NT name, i.e. devices and pipes; `Dxgk*` types get `IDI_DIRECTX`). The Threads tab's leftmost column likewise shows an icon per thread state (`CThreadsPage::GetRowImage`), from an image list of the page's own, because the page also runs on a property sheet's thread. Highlighting and the `HandleColumns` setting work as in the other pages. Handles and Modules are enumerated only while their tab is active; the pane does nothing while hidden, and a selection change reaches it after 150 ms (`DetailsTimerId`), so keyboard navigation doesn't enumerate every process it passes.
  - **Row colors** (`ProcessColors.*`): each `ProcessItem` keeps its `ProcessKind` flags, worked out at refresh time so `OnCustomDraw` only looks up the table: Secure, Protected (`PROCESS_EXTENDED_BASIC_INFORMATION`, one cached query in `ProcessInfoEx`), Immersive and Job when the item is added; Service from the PIDs of active services (`EnumServices`, done again on the update when processes start and the next one, since a service host is a new process); .NET from the `dotnet-diagnostic-<pid>` pipes (.NET Core and later) or the CLR's `Cor_Private_IPCBlock[_v4]_<pid>` section in the process's session (.NET Framework), checked again on every update while a process is younger than 15 s, because the runtime starts after the process. The exited and new highlights are kinds too (`Exited`, `New`, added in `OnCustomDraw`), so the first enabled kind in `ProcessColors::Defaults` order (Exited, New, Secure, Protected, Immersive, .NET, Services, Jobs) gives the color, light or dark. The `ProcessColors` setting holds `Key:enabled:RRGGBB:RRGGBB` per kind (keys must not change); Options > Process Colors... opens `CProcessColorsDlg` (`ProcessColorsDlg.*`): a check box per kind to use its color (Jobs off by default) and owner-drawn swatches for the light and dark colors that open the color dialog, and a Default button per row that restores its colors (not its check box), enabled while they differ from the defaults; the template's `IDC_PCOLOR_*` ranges follow the `Defaults` order. After OK the frame saves the setting and tells the views through `IView::OnProcessColorsChanged`.
  - **Process commands:** the Process menu (after View) and the row context menu both hold Kill, Kill All with the Same Name (by image name, case-insensitive), Suspend, Resume, Set Priority and Open File Location; `UpdateUI` enables the menu's items (and checks the priority) for the selected process, on selection changes and refreshes, and disables them while another tab is active.
  - **Process properties** (`ProcessSheet.*`, `ProcessPages.*`): double-clicking a process, View > Properties (Alt+Enter) or the context menu's Properties opens `CProcessSheet`, a modeless WTLHelper `CIconPropertySheetImpl` over `CResizablePropertySheetImpl` (tab icons, resizable, a Close button only), on a thread of its own with its own message loop (`ShowProcessProperties`). It has no owner and its own taskbar button. The sheet gets a `ProcessProperties` copy made on the UI thread, never the snapshot (the frame's `ProcessManager` isn't thread-safe); pages query anything else from the process themselves. WTLHelper's theming hook is per thread, so the sheet's thread installs it with `WTLHelper::InitThread` (and removes it with `TermThread`); only the sheet's title bar is set by hand. The General page lays out its controls with WTL's `CDynamicDialogLayout`, from the `AFX_DIALOG_LAYOUT` resource of `IDD_PROC_GENERAL` in `WinSysLive.rc`: four percentages (move X/Y, size X/Y) per control, in the template's order, so a control added to the template needs its row there too. Pages: General (implemented: identity, the ASLR/CFG/CET/DEP mitigation policies (`GetProcessMitigationPolicy`, plus the image header's DYNAMIC_BASE and HIGH_ENTROPY_VA for ASLR), signature verification on demand (`Signature.*`: WinVerifyTrust on the embedded signature, else the system catalog that lists the file's hash; no revocation checks) and Kill, which checks the process's start time so a reused PID isn't killed) Environment (`CProcEnvironmentPage`: a `CVirtualListView` of the variables from WinSys `Process::GetEnvironment`, read when the page is first shown; Copy and Copy All put `NAME=value` lines on the clipboard; it uses no `WS_EX_COMPOSITED`, which slows list views), Token (`CProcTokenPage`, filled once: the token's properties from WinSys `Token` and `LsaSecurity::GetLogonSessionData` in read-only edits, grouped in Identity, Logon, Token and Security boxes in one column on the left, and on the right two plain report lists, one above the other: its privileges with their descriptions, and its groups followed by an AppContainer's capabilities; the template and its `AFX_DIALOG_LAYOUT` (the properties stretch with 40% of the extra width, the lists take the rest and all the extra height, 40% of it the privileges') were generated, so keep the two in step when changing either; the token is opened through a limited-access process handle, with `TOKEN_QUERY_SOURCE` if allowed; an AppContainer's package name comes from `AppContainerLookupMoniker`, exported by kernelbase but in no SDK header, so it's resolved at run time) Performance (`CProcPerformancePage`: CPU (kernel and user, stacked), memory (private and working set), I/O (read, write, other) and network (receive and send, from the shared tracker, so only elevated) graphs, the Performance tab's graph classes from `PerfPages.h`, with the current values in three lines below; two columns of graphs when the page is wide enough, one while the One column check box is checked (not saved, as the settings belong to the UI thread); created with the sheet (`PSP_PREMATURE`), so the graphs have history from the moment it opened) Threads (`CProcThreadsPage`: the lower pane's `CThreadsPage`, fed through `Update` with the sheet's snapshot while the page is shown; once the process is gone the last threads stay; its columns start from the `ThreadColumns` setting, copied into `ProcessProperties` with the interval on the UI thread, and changes to them aren't saved (`UseColumns`), as the settings belong to the UI thread) Memory (`CProcMemoryPage`, `MemoryPage.*`: the address space from `VirtualQueryEx` in a TreeListView (an allocation's first region at the top level, its other regions as children, collapsed; a mapping's file on its first region, mapped to a drive letter by the page itself, as WinSys `Helpers::GetDosNameFromNtName` builds its table unlocked) beside a read-only HexControl, in a vertical splitter; the selected committed region's bytes are read as they're shown (`ProcessMemoryBuffer`, 64 KB chunks; guard and no-access regions aren't read, as a read would clear a guard page's guard; at most 256 MB of a region); the hex view shows the addresses (`SetBiasOffset`) and 16 bytes a line when they fit, 8 otherwise (`CMemoryHexView`, on every resize); the map is read when the page is first shown and on Refresh, which keeps the selection by address; the splitter's first position is set then too, as the page has its template's size in `WM_INITDIALOG`) Job (`CProcJobPage`, `JobPage.*`, added only for a process in a job: no API opens a process's job, so when the page is first shown it scans the system handle table for Job handles, duplicates them with `JOB_OBJECT_QUERY` from their owners (`PROCESS_DUP_HANDLE`, so mostly only when elevated) and keeps those `IsProcessInJob` accepts, told apart with `NtCompareObjects`; for nested jobs that's the job and its ancestors, listed in a combo box innermost first (the fewest active processes; nothing documented gives a job's parent, so when two have as many processes the jobs aren't labeled innermost and by nesting level); a single job's name is shown in a read-only edit instead. The limits that are set (extended limits, CPU and network rate, I/O rate, UI restrictions), the accounting statistics with the job's memory, and the job's processes (with values from the sheet's snapshot, `ProcessSnapshot::Find`) are read again on every sample while the page is active; the lists' texts are updated in place) and Service(s) (`CProcServicesPage`, `ServicesPage.*`, added only for a process hosting running services, titled by their number: the services in a list, with a Service DLL column for svchost.exe, and the selected one's details below it: configuration, description, the service DLL (the `ServiceDll` value of its key or its `Parameters` subkey, a user service instance's from its template's key) with its version strings (`ReadVersionInfo`, as `GetCachedVersionInfo` belongs to the UI thread), controls accepted, SID type, required privileges, triggers (repeats counted) and the service SID; read when the page is first shown and on Refresh, which keeps the selection by name; Start and Stop control the selected service, like the Services view without confirmation, after which the states are polled every 500 ms (for up to 30 s) until none is pending, then all is read again; a service stopped from the page stays listed (`m_Known`), and one running in another process shows its PID). The sheet takes a `SystemExtendedProcessInformation` snapshot every `UpdateInterval` (`ProcessSnapshot`, finding the process by ID and creation time, and stopping once it's gone) and hands it to the Performance page every time and the Threads and Job pages while they're active; the interval and the `ThreadColumns` setting are copied into `ProcessProperties` on the UI thread. `Run` calls `CloseProcessProperties` after the message loop: it ends the sheets' loops (`WM_QUIT`) and joins their threads, because a sheet left open while the app shut down lost its window under its loop. The view's own commands are in `ALT_MSG_MAP(1)`, so a `WM_COMMAND` posted to the view itself is ignored: the double-click calls `OnProperties` directly. Pages that override `OnSetActive`/`OnKillActive` follow WTL's default `_WTL_NEW_PAGE_NOTIFY_HANDLERS` meanings: `OnSetActive` returns an `int`, 0 to allow, and `OnKillActive` returns FALSE to allow leaving (TRUE keeps the user on the page).
  - **Column data:** most columns read the snapshot (`NativeInfo`: times, I/O transfer counts; `ExtendedInfo`, only when elevated: the job ID, else the column shows only whether the process is in a job). Values that need the process opened or a file read (architecture, integrity level, protection, UAC virtualization, description from the version resource) are cached in `ProcessInfoEx`; descriptions are also cached per image path. Values that change (GDI/User objects, memory and I/O priority) are queried on each call through one limited-access handle `ProcessInfoEx` keeps open. Non-elevated, system and protected processes can't be opened, so those columns are empty for them. Context switches are the process total when elevated (`ExtendedInfo`), otherwise the sum over the snapshot's threads (`SYSTEM_EXTENDED_THREAD_INFORMATION`); the delta columns are computed per `ProcessItem` on each refresh. The network columns come from WinSys `ProcessNetworkTracker` (ETW), which the view holds only while one of them is shown; it needs elevation, so non-elevated they stay empty. The tracker is shared with the property sheets (`NetworkTracking::Acquire`, `NetworkTracking.*`): its session is named after the app's process, so a second tracker would take it over; it stops when its last owner lets go.
- **Services view** (`ServicesView.*`) is a plain owner-data list view built on `CVirtualListView` and `ColumnManager`, the TotalPE pattern. On each refresh it enumerates services again and merges the result by name. Each service's configuration and description cost a call to the Service Control Manager, so they're loaded on first display and cached (`ServiceItem::GetConfig`). Selection is restored by service name: `GetSaveColumnRange` returns -1 to turn off `CVirtualListView`'s own restore. Restarting a service polls with a timer rather than blocking. Columns work as in the Processes view (`ColumnLayout`, the `ServiceColumns` setting; Name and State are mandatory): `SetColumns` rebuilds the `ColumnManager` with only the shown columns, in display order, which clears the sorting. The header's right-click arrives as `WM_CONTEXTMENU` from the list view (its `NM_RCLICK` never reaches `CVirtualListView`), so it's told apart from a row's by the position. Required privileges and triggers are loaded on first display and cached like the configuration; triggers show only type and action, because WinSys `ServiceTrigger::TriggerSubtype` points into a buffer `GetTriggers` frees. Double-clicking a service, or "Go to Process", calls `IMainFrame::GoToProcess`, which switches tabs and calls `IView::ShowProcess`.
- **Users view** (`UsersView.*`): a TreeListView with a row per session (WinSys `SessionManager`, `<WinSys/Sessions.h>`) and the session's processes as its children, like Task Manager's Users tab; the session rows show totals of their processes (the Idle process is left out). Each refresh enumerates the sessions without details, and gets the details (logon time, client name) only for a new session or one whose state or user changed: those queries raise and handle RPC exceptions (0x6BA) for sessions without a client. New sessions start collapsed (the TreeListView expands a new parent), except the user's own at startup. Disconnect and Log Off ask first. Keyboard context menus come as `WM_CONTEXTMENU` with -1, -1; mouse ones as `NM_RCLICK`.
- **Performance view** (`PerfView.*`, `PerfNav.*`, `PerfPages.*`): a list of pages on the left (`CPerfNav`, a custom-drawn window with a small history graph for each resource, which scrolls when the items don't fit) and the selected page on the right. Summary shows CPU, memory, network and total disk transfer, in a 2×2 grid when the page is wide enough. The selected page is saved in the `PerfPage` setting.
  - `CPerfView` takes one `PerfSample` per refresh tick from WinSys `SystemInfo` (per-processor times queried for each processor group, plus performance, basic and memory list information) and hands it to **every** page, also hidden ones, so their graphs have history when shown.
  - Pages implement `IPerfPage` through the `CPerfPage<T>` base (background, text lines below the graphs, layout): Summary, CPU, Memory, Network and one per drive. To add one (GPU...), add the data to `PerfSample`, write the page class, and add a nav item and a `m_Pages` entry in the same order (`NavItem`).
  - Graphs are GraphControl's `CGraphControl`, `CGraphGrid` and `CCompositionBar` from wtlhelper, included as `<GraphControl/include/...>`. Each graph keeps its own history, so a graph shown on two pages is two controls fed the same sample.
  - Network data comes from WinSys `NetworkTracker` (`<WinSys/Network.h>`, `GetIfTable2`, about 4 ms per tick), owned by the view; the sample points to its interface list. The Network page graphs only adapters that are up, and creates or destroys their graphs as that set changes.
  - Drive pages come from WinSys `DiskTracker` (`<WinSys/Disk.h>`). They're dynamic: `SyncDiskPages` inserts and removes pages and nav items, in drive letter order from `FirstDiskItem`, when drives appear or disappear. That's why the view keeps `m_Theme` and `m_TimeSpanText`, which pages created later need.
  - All pages are kept sized, not just the visible one, because laying out the per-processor grid is slow. The CPU page sets the grid's layout from its aspect ratio, because the grid's automatic layout is square.
- **Painting performance:** WTLHelper installs a thread-wide `WH_CALLWNDPROCRET` hook to theme new windows. While it's installed, every `SendMessage` goes through the kernel, and that roughly doubled the time to repaint the process list. For any list with many rows or callbacks, call `SuspendHookWhilePainting(hList)` from `ViewBase.h`; it removes the hook during `WM_PAINT` (`WTLHelper::SuspendHook` really unhooks). Measured per refresh tick with the Processes tab visible: ~20 ms for the snapshot (on the UI thread) and ~60 ms for painting.
- **Adding a tab** takes four steps:
  1. Add a value to `TabType` (`Interfaces.h`).
  2. Write `XxxView.h/.cpp`.
  3. Add a `case` to `CMainFrame::CreateView` (`ViewFactory.cpp`).
  4. Add an entry to `CMainFrame::s_Tabs`, an `ID_VIEW_*` command (View menu item and Ctrl+N accelerator) and a `COMMAND_ID_HANDLER(ID_VIEW_*, OnViewTab)` in the frame's message map.

## Conventions

- Every `.cpp` starts with `#include "pch.h"` (ATL/WTL and STL headers live there).
- Classes use WTL style: `C` prefix, `m_` members, message maps with the commented handler-prototype boilerplate, tabs for indentation, and opening braces on the same line.
- New command IDs go in `resource.h` and the menu in `WinSysLive.rc`. When adding a source file, register it in both `WinSysLive.vcxproj` and `WinSysLive.vcxproj.filters`.
