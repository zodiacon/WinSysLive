# The Processes view

The Processes tab in detail: its tree, filter, hiding, columns, row colors, the lower pane (Handles, Modules, Threads), the process commands and the process property sheet with all its pages. Read it before changing `ProcessesView.*`, `ProcessDetails.*`, the lower pane's pages or `ProcessSheet.*`/`ProcessPages.*`.

- **Processes view** (`ProcessesView.*`) uses the standalone TreeListView (`CTreeListViewCtrl`) in callback mode (`TLVN_GETDISPINFO`). Item data is a `ProcessItem*` stored in an `unordered_map`, whose element pointers stay valid. Points to watch:
  - **Filter:** a `CFilterBox` (`FilterBox.*`, shared with the Services view) in the view's own rebar (`CreateSimpleReBar`; the view is a `CFrameWindowImpl`): an edit applied 250 ms after typing stops (a timer on the edit itself), whose `EN_CHANGE` comes to the view through the rebar and is handed back to `Changed`; it calls the view with the lowercase text. A process matches if its image name, PID, user, description or command line contains the text (case-insensitive); `ProcessItem::Match` keeps the result. Every process stays in `m_Items` (deltas, kinds); only matching ones are inserted, and `EnsureInserted` brings their ancestors along (gray when they don't match themselves and have no kind color), so items may have no `Item`. New processes are matched as they appear; Go to Process clears a filter that hides the target. View > Hide Processes, also the Hide drop-down button beside the filter (`m_HideBar`, a one-button toolbar in a second rebar band, checked while an option is on; its menu is that submenu, loaded from `IDR_MAINFRAME`; the view's `UpdateLayout` maximizes its band after every layout, as the rebar gives a row's extra width to the first band, the filter's), hides (`IsHidden`, the `ProcessHide*` settings) other users' processes (no Own kind), services' (the Service kind), Windows processes (the image in the Windows directory, or none: Idle, System, Registry...) and signed ones (a valid signature, verified by a `SignatureVerifier` (`SignatureVerifier.*`, the Kernel Modules view's too: WinSys `FileSignature` on a worker thread, results by path, posting `WM_PROCESS_SIGNED`); shown until verified). A hidden item doesn't match (`ProcessItem::Hidden`), so it's in the tree only as a gray ancestor; as the kinds and the signatures change, `UpdateHidden` puts items into the tree or takes them out (on every refresh, and on `WM_PROCESS_SIGNED`), which is why the kinds are set before items are matched. The status line counts the shown processes while any option is on; Go to Process says so in the status line for a hidden process rather than showing it. Ctrl+F (`ID_EDIT_FIND`) focuses the box; Escape clears it (empty: back to the list), Enter and Down go to the list. The status line's first pane counts the matches. `CMainFrame::PreTranslateMessage` leaves editing keys (Space, Delete, Ctrl+C/V/X/A/Z/Y) to an edit control with the focus, as they're accelerators otherwise.
  - **Removing an item:** `DeleteItem` removes the whole subtree, so `RemoveItem` re-inserts the children first.
  - **Exited processes** are shown for `Highlight::ExitedTicks` refreshes (`ProcessItem::ExitTicks`), then removed. Their `NativeInfo` points into the previous snapshot buffer, which the next `Update()` overwrites, so the refresh that finds a process exited calls WinSys `ProcessInfo::Detach`, which copies its entry into a buffer of its own (with a duration of zero the item goes at once).
  - **Selection:** the inner list view tracks the selection by row index, so after any insert, delete or sort, restore it by item with `SelectItem(h, false)`. An update keeps the scroll position (TreeListView passes `LVSICF_NOSCROLL` whenever it resets the item count, which otherwise scrolls the focused row into view); with View > Keep Selection Visible (the `ProcessKeepSelectionVisible` setting, shared with the Object Manager view, so both read the setting rather than keep a copy) it scrolls to the selection instead. Rebuilding the list (tree/flat) and a sort from the header always show the selection.
  - **Flat mode** rebuilds the list with every item at the top level, because TreeListView's own flat mode sorts only within each parent.
  - **Image list:** the inner list view has `LVS_SHAREIMAGELISTS` set, since the image list belongs to the frame.
  - **Columns:** `m_Columns` maps list columns to `Column` values; Name is always list column 0, because that column draws the tree, and Name and PID can't be hidden. The display order is the header's order array (the user can also drag columns). Right-clicking the header shows a menu to hide that column or open the dialog; the header's `WM_CONTEXTMENU` reaches the view with the TreeListView as `wParam`, so `OnContextMenu` tells it apart from a row's by the position. View > Select Columns opens the column dialog: `ColumnLayout::Select` runs `CColumnsTreeDlg` (`ColumnsTreeDlg.*`) when the table's `ColumnDef`s have a `Category` (only the Processes table so far, in the order the view passes: General, CPU, Memory, I/O, Network, GPU and NPU, Handles and Objects, Security), else `CColumnsDlg` (`ColumnsDlg.*`, a generic check list with a search box, Move Up/Down and Defaults). The tree has the categories collapsed, titled with how many of their columns are shown, and their columns under them, all with check boxes (`TVS_EX_PARTIALCHECKBOXES`: a category's box is partial while only some are shown; clicking a checked one clears it, any other checks all; mandatory columns stay checked); the search keeps the matching columns with their categories expanded; it has no Move Up/Down: the header's drag and drop orders the columns, and newly checked ones go after the shown ones. The shown columns, in display order with their widths, are saved in the `ProcessColumns` setting as `Key:width,...` (keys in `s_Columns`, which must not change), after the dialog and when the view is destroyed. Parsing, saving and running the dialog are shared with the Services view and the lower pane's pages in `ColumnLayout.*` (a table of `ColumnDef`, with `Mandatory` columns that can't be hidden), which also has the helpers for a `CVirtualListView` list whose `ColumnManager` holds only the shown columns: `GetShownColumns`, `SetColumns`, `HeaderColumnAt` (a header's `WM_CONTEXTMENU` is told from a row's by the position) and `PrepareHeaderMenu`. `SetColumns` sets column 0's alignment again after inserting it, because the list view ignores it on insertion. The header menu (IDR_CONTEXT's Column popup, every list's) also has Reset to Defaults (`ID_COLUMN_RESET`): each list's `OnResetColumns`, beside its `OnHideColumn`, sets the columns `ColumnLayout::Parse` gives for no layout (the table's defaults, in their order and widths) and saves them.
  - **Lower pane:** the client is a `CCustomHorSplitterWindow` (WTLHelper) with the tree on top and `CProcessDetails` (`ProcessDetails.*`, a `CNativeCustomTabViewImpl` with Handles, Modules and Threads list views) below. View > Lower Pane (Ctrl+L) switches the splitter to single-pane mode; the `ProcessLowerPane` and `ProcessSplitterPos` settings keep it. The splitter forwards the tree's `WM_NOTIFY` to the view. `UpdateDetails` hands the selected process (none for an exited one) to the pane after selection changes and refreshes; `SetProcess` ignores the same process, as the selection is restored on every refresh. Don't give `CProcessDetails` a message map of its own: the tab view's has an `ALT_MSG_MAP(1)` that it routes to, and a map without it asserts. The Threads tab is `CThreadsPage` (`ThreadsPage.*`), a window owning a virtual list view (`CVirtualListView`, sorting by the column manager's tags): each refresh it copies the selected process's threads from the snapshot (the `SYSTEM_EXTENDED_THREAD_INFORMATION` array after the process entry; the frame's `Update()` doesn't build thread objects, which would cost thousands of allocations per tick), and computes CPU and the context switch delta from the previous refresh's values, kept per thread key, over the elapsed QPC time. The start address is the snapshot's `Win32StartAddress` (else `StartAddress`), which only an elevated caller gets (zero otherwise): when it's zero, it's queried once from the thread (WinSys `Thread::GetStartAddress`, `ThreadQuerySetWin32StartAddress`, which needs `THREAD_QUERY_INFORMATION`: so not for other users' or protected processes' threads) and kept in the thread's state. Ideal CPU, I/O and memory priority and cycles come from a WinSys `Thread` handle per thread (query access, else limited), opened once while the process is shown and kept in the per-thread state; the service (from the TEB's SubProcessTag) is queried once per thread. COM Apartment (shown by default, table version 1) is read every refresh while it's shown (a thread may initialize or leave COM any time): the process is opened once (`PROCESS_VM_READ`, `m_hProcess`, again for another process, closed while the column is hidden), each thread's TEB address queried once (`Thread::GetTebAddress`, kept in its state) and its COM flags read from it (`Thread::GetComFlags`, the 32-bit TEB's for a WOW64 process), worded by `Thread::ComApartmentText`: STA, ASTA, MTA, with WinRT, a call in the neutral apartment and uninitializing said; a thread that didn't initialize COM is Implicit MTA when another of the process's threads is in the MTA (`m_HasMta`, from the same refresh); nothing when they can't be read (another user's process when not elevated, a protected one). New threads are highlighted for two refreshes (not on a process's first refresh); a thread that exited is shown once more as a red row from its last values, its state kept for that refresh in `m_Exited` (the row points to its Service string). The selection is restored by thread ID. The states' and wait reasons' names, the state icons and the row menu's commands (Stack, Wait Chain, Suspend and Resume, Terminate, Set Priority, Affinity) are `ThreadCommands` (`ThreadCommands.*`), shared with the Threads tab. Its columns work like the Services view's (`ColumnLayout`, the `ThreadColumns` setting, TID mandatory), chosen from the header's context menu only (View > Select Columns belongs to the process list); that menu posts its commands to the page, because a dialog run with `TPM_RETURNCMD` inside the header's right-button handling didn't paint. CPU History (hidden by default) is the Threads tab's sparkline (`CpuHistory.h`, see docs/views.md): the series in each thread's `ThreadState`, pushed in `Update` while the column is shown, found for a row by its key among the running and the exited threads (`FindState`); the sheet's page has it too, drawn on the sheet's thread. The Modules tab is `CModulesPage` (`ModulesPage.*`), built the same way on WinSys `ProcessModuleTracker` (one per selected process; it walks the address space, so it's enumerated only while its tab is active, and on activation through `OnPageActivated`): images and mapped data files (page-file-backed sections left out), version strings from `GetCachedVersionInfo` (`VersionInfo.*`, cached per path, also used for the process Description), new modules highlighted for two refreshes and unloaded ones shown for one, columns in the `ModuleColumns` setting; the leftmost column shown has the mapping type's icon from the frame's image list (`IDI_MODULE_IMAGE`, `IDI_MODULE_DATA`; the page gets the frame through `SetFrame`, as the Handles page does). The Handles tab is `CHandlesPage` (`HandlesPage.*`) on WinSys `HandleEnumerator`: the process's own handle snapshot, or the system handle table (about 33 ms for ~360,000 handles) only while the Address column is shown (its addresses are null unless SeDebugPrivilege is enabled, elevated or not, since Windows 11 24H2: `_tWinMain` enables it at startup); `CHandleSheet` looks the address up there itself when its entry has none. Names are queried when a row is shown or sorted, through a duplicate of the handle, once per handle: processes and threads by ID and image name (duplicated with query access, so handles without it still show their IDs; the image name from the snapshot, else from the handle), tokens by user and logon session, files as DOS paths, keys as `HKLM\`/`HKCU\`/`HKU\`, the rest by their object names; files through WinSys `ObjectNameQuery` (100 ms timeout; files aren't queried after 4 hung queries), other types directly, as only a file's query can hang. That logic is WinSys `HandleNames::QueryName`, shared with Find Handle or DLL and safe on any thread (with `DosNames`, a drive table of its own, and `RegistryName`); the Memory page uses `DosNames` too for mapped files. WinSys `AccessMaskDecoder` decodes access masks per type. The leftmost column shown (wherever the user drags the columns: `ColumnLayout::IsLeftmostColumn`) has an icon per object type from the frame's image list (`GetHandleIcon`, in `HandleIcons.*`; `IDI_OBJECT` for types without one of their own; files get `IDI_DEVICE` when their name stays an NT name, i.e. devices and pipes; `Dxgk*` types get `IDI_DIRECTX`). The Threads tab's leftmost column likewise shows an icon per thread state (`CThreadsPage::GetRowImage`), from an image list of the page's own, because the page also runs on a property sheet's thread. Highlighting and the `HandleColumns` setting work as in the other pages. View > Show Unnamed Handles (`ID_VIEW_SHOWUNNAMEDHANDLES`, also in the page's context menu, which offers it alone without a selected row; the `ShowUnnamedHandles` setting, on by default) unchecked lists only the handles whose Name / Details text isn't empty (`Matches`, which then queries every handle's name); a sheet's Handles page gets the setting's copy (`UseShowUnnamed`, from `ProcessProperties`) and doesn't save its changes. By Type (the page's context menu, `ID_HANDLE_BYTYPE`; not saved) shows a summary in the handle list's place, `m_Types`, a plain report list with an ID of its own (`TypesId`) whose notifications a `NOTIFY_ID_HANDLER` first in the map takes, as `CVirtualListView`'s handlers would adopt it as one of their lists: per object type (with its icon) the open handles, the change since the previous refresh and since a baseline (the first count after the process was selected, or Reset Baseline, which restarts the peaks too), and the peak, counted on every refresh from the rows the page has (`CountTypes`; a type whose handles all closed stays, at 0), the change cells green up and red down as on the Object Types tab (subitem custom draw, the other cells given back the row's colors), so a leaking type stands out; sorted by count until a header is clicked, the filter matching the type, the selection kept by type. Show Handles (also a double-click) goes back to the handle list with the filter set to the type (`CFilterBox::SetText`), matching the type exactly while the filter is its name (`m_OnlyType`). A toolbar right of the filter box (`m_Bar`, WTLHelper `ToolbarHelper::CreateAndInitToolBar`: check buttons with an icon and text, `IDI_OBJECT` and `IDI_HANDLES` at 16 pixels for now; the control font for the page's DPI; icons and font made again on `WM_DPICHANGED_AFTERPARENT`) has By Type and Unnamed Handles, sending the context menu's commands and checked as the options are (`UpdateBar`, wherever they change). The filter keeps its width (200 at 96 DPI); the bar takes the rest of the row, to the right edge, the gap as its indent, as anything of the row left uncovered showed the page's unpainted (white) background in dark mode; `OnEraseBkgnd` fills the row's strip with `COLOR_WINDOW` (dark under WTLHelper) for the gaps around a shorter filter box (`Layout`, `m_RowHeight`). Double-clicking a handle, its row menu's Properties or View > Properties (Alt+Enter, routed by `GetKillTarget` while the page has the focus) opens `CHandleSheet` (`HandleSheet.*`), a modal, resizable property sheet with tab icons (WTLHelper `CIconPropertySheetImpl` over `CResizablePropertySheetImpl`) and three tabs; the sheet and the details tab have the type's icon (`GetHandleIcon`), General `IDI_HANDLES`, and Security the system's shield (`IDI_SHIELD`), set in `OnSheetInitialized` because the ACL editor's `HPROPSHEETPAGE` brings no icon the sheet knows. General (the handle and the object) and the type's details (titled by the type: Mutex, Named Pipe, File..., the type's own name when it has no details, followed by the type's statistics: counts, valid access, generic mapping, pool) are `CHandleListPage`s: WinSys `ObjectInspector::QueryHandle` laid out as property lists (`CDialogResize`; bold, shaded section rows on General), where Refresh queries again for both and Copy copies the selected row (a property's name and value, tab separated, or a section's `[title]`; also Ctrl+C), Copy Value its value and Copy All every row, `[Section]` titles and tab-separated properties (the list's context menu has the three; Refresh keeps the selected row); a type whose details the handle's access doesn't allow gets a Not Available row. Security is the system's ACL editor page (`CreateSecurityPage`) on a `CObjectSecurityInfo` (`ObjectSecurity.*`) over a duplicate of the handle (`ObjectInspector::OpenHandle`), which the counts leave out (`QueryHandle`'s `ownHandles`), as they do the query's own. Apply or OK writes changes made there. The row menu also has Close Handle. Each of the three pages has a filter box above its list (`CFilterBox`, a child of the page; Ctrl+F focuses the filter of the page with the focus, through `CProcessesView::OnFind`): a row matches if any shown column contains the text. A page keeps every row of its last refresh (`m_AllRows`) and shows the matching ones (`ShowRows`, which also sorts and keeps the selection), so a filter change doesn't refresh (the Threads page's deltas and the highlighting go by refreshes). The pages' row menus have Copy (the row's shown columns, tab separated: `ListExport::RowText`); the Modules page's also has Properties (the shell's, `SHObjectProperties`; also on a double-click), Open File Location, Image Details... (`ID_MODULE_IMAGE`, `CPEFileDlg`) and Open in TotalPE (`ID_MODULE_TOTALPE`; the Drivers tab's menu has Image Details... too, `ID_DRIVER_IMAGE`, for the driver's file loaded or not, and the Kernel Modules tab's, `ID_KMODULE_IMAGE`, `TotalPE::Open` as the Image page's button; images only, grayed for the mapped data files such as the .NLS locale tables, which come first in the list); being `CModulesPage`'s, it's in the lower pane and the process sheet alike. Each page is refreshed only while its tab is active, and when it's activated (the Threads page's deltas cover the time since its last refresh); the pane does nothing while hidden, and a selection change reaches it after 150 ms (`DetailsTimerId`), so keyboard navigation doesn't enumerate every process it passes.
  - **Row colors** (`ProcessColors.*`): each `ProcessItem` keeps its `ProcessKind` flags, worked out at refresh time so `OnCustomDraw` only looks up the table: Secure, Protected (WinSys `Process::IsSecure`/`IsProtected`, cached in `ProcessInfoEx`), Immersive, Job and Own (the user is the app's own entry's, `GetUser`, so the formats match) when the item is added; Suspended on every refresh (every thread Waiting for Suspended or WrSuspended, as a suspended process's or a frozen Store app's); Service from the PIDs of active services (`EnumServices`, done again on the update when processes start and the next one, since a service host is a new process); .NET from WinSys `DotNetInfo`: the `dotnet-diagnostic-<pid>` pipes (.NET Core and later, `GetCoreRuntimeProcesses`) or the CLR's `Cor_Private_IPCBlock[_v4]_<pid>` section in the process's session (.NET Framework, `HasFrameworkRuntime`; the .NET Framework 4 CLR on current Windows puts it in a private namespace instead, so it finds only older CLRs), else clr.dll, mscorwks.dll or coreclr.dll among its modules (`HasRuntimeModule`, a few milliseconds a process), checked again on every update while a process is younger than 15 s, because the runtime starts after the process. The module check of every process (at startup, and when the color is turned on in the colors dialog: `OnProcessColorsChanged`) runs on a `std::jthread` (about 2 s for 500 processes; `WM_DOTNET_SCANNED` marks the processes found, by ID and creation time); new processes are checked inline. The .NET kind is only a color, so nothing is checked while its color is off, which is its default (`ProcessColors::Defaults`). The exited and new highlights are kinds too (`Exited`, `New`, added in `OnCustomDraw`), so the first enabled kind in `ProcessColors::Defaults` order (Exited, New, Tampered, Suspended, Secure, Protected, Immersive, .NET, Services, Jobs, Own) gives the color, light or dark. The `ProcessColors` setting holds `Key:enabled:RRGGBB:RRGGBB` per kind (keys must not change); Options > Process Colors... opens `CProcessColorsDlg` (`ProcessColorsDlg.*`): a check box per kind to use its color (Jobs off by default) and owner-drawn swatches for the light and dark colors that open the color dialog, and a Default button per row that restores its colors (not its check box), enabled while they differ from the defaults; the template's `IDC_PCOLOR_*` ranges (blocks of eleven IDs, one per kind, renumbered to 1511-1554 when Tampered came) follow the `Defaults` order, so a new kind needs a row in the template and the ranges renumbered. After OK the frame saves the setting and tells the views through `IView::OnProcessColorsChanged`.
  - **Process commands:** the Process menu (after View) and the row context menu both hold Kill, Kill Process Tree (the root first, then its descendants from the snapshot by parent ID and creation time, the app's own process left out), Kill All with the Same Name (by image name, case-insensitive), Restart (WinSys `Process::Restart`: the image, command line, current directory and environment read, the process terminated and created again by the app, with its account and elevation; not for services' processes, packaged apps or the app itself), Suspend, Resume, Set Priority and Open File Location; `UpdateUI` enables the menu's items (and checks the priority) for the selected process, on selection changes and refreshes, and disables them while another tab is active.
 The toolbar's Kill button and Del are `ID_KILL`, which acts on the list with the focus (`GetKillTarget`): the process tree kills the process (as `ID_PROCESS_KILL`, which the Process menu keeps), the lower pane's Threads page terminates the thread (`CThreadsPage::TerminateSelected`, the context menu's command), its Handles page closes the handle in its process (`CHandlesPage::CloseSelected`: WinSys `HandleNames::CloseInProcess` after a confirmation, which closes it only if the value still refers to an object of the row's type; not the app's own handles), and the Modules page does nothing. The focus changes without the view being told, so the frame calls the active view's `IView::OnFrameIdle` from its idle handler, where the view enables `ID_KILL` (`OnIdle` is taken: `CViewBase`'s idle handler). Its toolbar tooltip says what it would do (Kill Process, Terminate Thread, Close Handle): the frame answers `TTN_GETDISPINFO` for `ID_KILL` itself with the active view's `IView::GetCommandTip`, never with `TTF_DI_SETITEM` (which `CFrameWindowImpl`'s handler sets, making the tooltip keep the text). Create Dump (Minidump, Full Dump) asks for a file (`name_pid_date_time.dmp`) and writes it with WinSys `MiniDump::Write` on the symbol engine's thread (`SymbolEngine::WriteDump`; DbgHelp isn't thread-safe), which posts `WM_DUMP_WRITTEN` to the view; a minidump has threads, modules, handles and memory info, a full dump all the memory. The menus also set, through a WinSys `Process` opened with `SetInformation` (`OpenSelected`), the I/O priority (`SetIoPriority`), the memory priority (`SetMemoryPriority`), the affinity (`CAffinityDlg`, `AffinityDlg.*`: a check box per processor, laid out at run time in rows of eight, all created in `WM_INITDIALOG`, as the theming reaches only the windows there are then; with more than one processor group (over 64 processors, WinSys `SystemInfo::GetProcessorGroups`) a combo box shows one group at a time, each keeping its selection, processors numbered across the groups. `SetGroupsAffinity` then sets a process held to one group by an affinity mask (`GetAffinity` succeeds) by that mask, its other groups shown disabled, and any other process (spanning the groups, which has no single mask) by its default CPU sets, `SetDefaultCpuSetMasks`, every processor clearing them) Reduce Working Set (`Process::EmptyWorkingSet`) and, in an Advanced submenu (same in the Process menu and the row menu), Critical Process (checked for a critical process, `Process::IsCritical`; enabled only when elevated, as `Process::SetCritical` needs SeDebugPrivilege; a confirmation either way: Windows crashes when a critical process exits; protected processes can't be opened for it) and Inject DLL... (`OnInjectDll`: a DLL chosen from a file dialog, injected with WinSys `Process::InjectDll`; the result reported, a 32-bit target or a failed load explained), Debug (`Process::AttachDebugger`: the AeDebug key's Debugger command line with the PID, without its crash-only arguments, after a confirmation that shows it) and Efficiency Mode (`SetEfficiencyMode`, as Task Manager: EcoQoS plus the Idle class; off: the system decides again, at Normal), with the current values checked (`ProcessInfoEx::GetEfficiencyMode`, the priorities through its handle).
  - **Process properties** (`ProcessSheet.*`, `ProcessPages.*`): double-clicking a process, View > Properties (Alt+Enter) or the context menu's Properties opens `CProcessSheet`, a modeless WTLHelper `CIconPropertySheetImpl` over `CResizablePropertySheetImpl` (tab icons, resizable, a Close button only), on a thread of its own with its own message loop (`ShowProcessProperties`). It has no owner and its own taskbar button. The sheet gets a `ProcessProperties` copy made on the UI thread, never the snapshot (the frame's `ProcessManager` isn't thread-safe); pages query anything else from the process themselves. WTLHelper's theming hook is per thread, so the sheet's thread installs it with `WTLHelper::InitThread` (and removes it with `TermThread`); only the sheet's title bar is set by hand. The General page lays out its controls with WTL's `CDynamicDialogLayout`, from the `AFX_DIALOG_LAYOUT` resource of `IDD_PROC_GENERAL` in `WinSysLive.rc`: four percentages (move X/Y, size X/Y) per control, in the template's order, so a control added to the template needs its row there too. Pages: General (implemented: identity, the ASLR/CFG/CET/DEP mitigation policies (`GetProcessMitigationPolicy`, plus the image header's DYNAMIC_BASE and HIGH_ENTROPY_VA for ASLR), signature verification on demand (WinSys `FileSignature::Verify`: WinVerifyTrust on the embedded signature, else the system catalog that lists the file's hash; no revocation checks; `Signature.*` words the result) Kill, which checks the process's start time so a reused PID isn't killed, and Security..., the process object's permissions in the ACL editor's own dialog (`EditSecurity` on a `CObjectSecurityInfo`, the process opened with the most of READ_CONTROL, WRITE_DAC and WRITE_OWNER it allows; a dialog, not a page of the sheet, as the editor's page doesn't follow the resizable sheet's size); the sheet has no Apply) Statistics (`CProcStatsPage`, `StatisticsPage.*`, after Performance: every counter in one owner-data list, in sections drawn bold and shaded as the handle sheet's (CPU: priority, times, cycles, context switches, threads; Memory: private bytes, virtual size, working set, page faults, pools, each with its peak, memory priority; I/O: operations and bytes by type, I/O priority; Handles and Objects: handles, GDI and USER objects with their peaks), from the sheet's snapshot and, for the peaks of handles (WinSys `Process::GetPeakHandleCount`) and GUI objects and the priorities, a limited-access handle opened once; fed every sample while active, the Change column against the previous sample shown (starting over when activated); Copy and Copy All) Environment (`CProcEnvironmentPage`: a `CVirtualListView` of the variables from WinSys `Process::GetEnvironment`, read when the page is first shown; Copy and Copy All put `NAME=value` lines on the clipboard; it uses no `WS_EX_COMPOSITED`, which slows list views), Token (`CProcTokenPage`, filled once (its Security... button opens the token's own permissions, `EditSecurity` on a `CObjectSecurityInfo`, the token opened with the most of READ_CONTROL, WRITE_DAC and WRITE_OWNER it allows): the token's properties from WinSys `Token` and `LsaSecurity::GetLogonSessionData` in read-only edits (labels for those with a fixed set of values: elevated, UI access, restricted, filtered, sandbox inert, token type, logon type, virtualization, integrity level, elevation type, mandatory policy); the trust level is the token's trust SID, and without one a protected process's protection after "None" (lsass runs as PPL with the Lsa signer, which no trust SID names, so its token has none), grouped in Identity, Logon, Token and Security boxes in one column on the left, and on the right two plain report lists, one above the other: its privileges with their descriptions (each with `IDI_ENABLED` or `IDI_DISABLED`, from an image list of the page's own, as it runs on the sheet's thread, rebuilt on `WM_DPICHANGED_AFTERPARENT`), and its groups (each with its SID kind's icon: `IDI_USER`, `IDI_GROUP` (a domain's too), `IDI_WELLKNOWN_GROUP`, `IDI_ALIAS`, `IDI_LABEL`, `IDI_LOGON_SESSIONS`, from an image list of the page's own as well) followed by an AppContainer's capabilities (`IDI_CAPABILITY`, `Power.ico`), in the token's order until the Privilege, Name or groups' Type header is clicked (those columns sort, case-insensitively, a click again reversing it, Type's ties by name; the others don't); the privileges' context menu enables or disables the selected one (WinSys `Token::EnablePrivilege`, by LUID, the token opened with `TOKEN_ADJUST_PRIVILEGES`), and Lower... beside the integrity level offers the levels below the token's (WinSys `Token::SetIntegrityLevel`, `TOKEN_ADJUST_DEFAULT`, after a confirmation: it can't be raised again, and the kernel disables the token's enabled privileges); both fill the lists again, keeping their sort and the selected privilege; the template and its `AFX_DIALOG_LAYOUT` (the properties stretch with 25% of the extra width, the lists take the other 75% and all the extra height, 40% of it the privileges') were generated, so keep the two in step when changing either;  Critical ("Yes", queried on each call like the priorities, so a change shows at once), Parent PID and Parent Name (the parent's name only while it runs: created before the child, `GetParent`), Paged and Non-Paged Pool (the snapshot's quota usage), Elevated ("Yes"/"No", with "(full)"/"(limited)" for a split token), CFG and Mitigations (WinSys `Process::GetMitigations`, queried once through the full query handle, else the limited one; Mitigations lists the rest: DEP, ASLR, CET, ACG, CIG...), DPI Awareness (WinSys `Process::GetDpiAwareness`, from the awareness context, so Per-Monitor v2 and GDI scaled show) and Package Name (the elevated snapshot's, else `Process::GetPackageFullName`) are cached in `ProcessInfoEx`; Window Title comes from WinSys `Process::GetMainWindowTitles` (one pass over the top-level windows per refresh while the column is shown, `m_WindowTitles`: each process's frontmost visible, unowned, non-tool window with a title).
 Status is Task Manager's (Details tab): Suspended from the Suspended kind, Not responding when the process has a visible top-level window that's hung (WinSys `Process::GetHungProcesses`, `IsHungAppWindow`, one pass over the windows per refresh while the column is shown), else Running; empty for an exited process.
 The GPU columns (GPU %, Dedicated and Shared GPU Memory) come from WinSys `GpuInfo::QueryProcess`, run on every refresh while one of them is shown (`ShowsGpu`): it needs a handle with `PROCESS_QUERY_INFORMATION` (a limited one gets `STATUS_INVALID_PARAMETER`; `ProcessInfoEx::GetQueryInformationHandle`, a WinSys `Process` opened once), and a process without GPU memory isn't queried for its engines, which keeps it to about 1% of a core with ~500 processes. NPU (%) and NPU Memory (dedicated and shared together) are the same query on the NPUs (`GpuAdapterKind::Npu`), made only while one of them is shown and there are NPUs (`ShowsNpu`).
 **History graph columns** (CPU History, Private Bytes History, I/O History, Network History) draw per-process sparklines with GraphControl's `CellGraphs` (`<GraphControl/include/CellGraphs.h>`): the view owns a `GraphCtrl::CellGraphs m_CellGraphs`, `OnCustomDraw` routes the tree's `NM_CUSTOMDRAW` through it (`CustomDraw(&cd->nmcd, cd->iSubItem, (UINT_PTR)cd->hItem, ...)`, after the row-color stage, so the sparkline draws over each cell's sub-item post-paint while the row keeps its kind color and selection), and a data callback maps a cell to its `ProcessItem`'s `Series`. Each `ProcessItem` keeps a `GraphCtrl::Series` per kind; `UpdateHistory` pushes a sample each refresh only while that column is shown (else it clears the series, so it grows in from the right when re-enabled): CPU the percentage (0-100), Private Bytes the absolute bytes (auto-scaled), I/O the total transfer-count rate and Network the send+receive rate (bytes/s over the update interval, with `PrevIoBytes`/`PrevNetBytes`; Network History turns the ETW tracker on through `ShowsNetwork`, so elevated only). `ConfigureCellGraphs` (from `SetColumns`) assigns a `SparklineStyle` and a `Format` (Percent, Bytes, BytesPerSec) to each shown history column by its list-column index; the cells still carry the current value as text (sorting by the underlying metric, export and screen readers), and `EnableTooltips` shows the samples' last/min/max/average on hover.
