# The other tabs

Each tab but Processes (see [processes-view.md](processes-view.md)), in detail. Read the tab's entry before changing it.

- **Services view** (`ServicesView.*`; also the Drivers tab, see below) is a plain owner-data list view built on `CVirtualListView` and `ColumnManager`, the TotalPE pattern. On each refresh it enumerates services again and merges the result by name. Each service's configuration and description cost a call to the Service Control Manager, so they're loaded on first display and cached (`ServiceItem::GetConfig`). Selection is restored by service name: `GetSaveColumnRange` returns -1 to turn off `CVirtualListView`'s own restore. Stop and Restart take the running dependents along (WinSys `Service::GetDependents`, after a confirmation that lists them): they're stopped first, in the SCM's order, then the service; a restart then starts the service and the dependents that ran, in the reverse order. `ServiceControlSteps` (`ServiceSteps.*`, also the process sheet's Services page's Stop) sends one control at a time, and the view polls it with a timer (each service waited for up to 30 s) rather than blocking; a stop that fails or times out ends the steps, and the starts that failed are reported at the end. Columns work as in the Processes view (`ColumnLayout`, the `ServiceColumns` setting; Name and State are mandatory): `SetColumns` rebuilds the `ColumnManager` with only the shown columns, in display order, which clears the sorting. The header's right-click arrives as `WM_CONTEXTMENU` from the list view (its `NM_RCLICK` never reaches `CVirtualListView`), so it's told apart from a row's by the position. Required privileges and triggers are loaded on first display and cached like the configuration; the Triggers column shows each trigger's type and action, those alike counted (WinSys `Service::GetTriggerDetails`; the subtypes and data are on the sheet's Triggers page). The row menu also has Start Type (Automatic, Automatic (Delayed Start), Manual, Disabled, the current one checked; WinSys `Service::ChangeConfig` and `SetDelayedAutoStart`) and Properties (Alt+Enter, enabled from the view's `OnFrameIdle`; the Processes view updates that command only while it's active): `CServiceSheet` (`ServiceSheet.*`), modal, as services.msc has it: General (display name, description, path, start type, error control), Log On (Local System, Local Service, Network Service or an account with its password, which stays unless typed again; read-only for a per-user service) Dependencies (`CServiceDependenciesPage`, for drivers too: two trees, what the service depends on, services and load order groups, and the services depending on it directly, sorted; a node gets its children when expanded, the direct dependents picked from `GetDependents`, which lists indirect ones too, by their configured dependencies, a load order group to its services (every service's group read once, on the first group expanded); double-clicking a service or its context menu opens its sheet, hit-testing the cursor's position), Security (the ACL editor's page on a `CServiceSecurityInfo`, `ObjectSecurity.*`: a `CObjectSecurityInfo` whose descriptor goes through WinSys `Service::GetSecurity`/`SetSecurity`, as the SCM's objects aren't kernel objects, with a service's rights and generic mapping; opened with the most of READ_CONTROL, WRITE_DAC and WRITE_OWNER it allows; the sheet installs `CAclDialogTheming`) and Triggers (`CServiceTriggersPage`, added only for a service with triggers: WinSys `Service::GetTriggerDetails`; each trigger's action, type and subtype, named for the documented subtype GUIDs (copied: `INITGUID` is off) and an ETW provider's registered name (`Service::GetEventProviderName`), and the selected one's data items below: a string item's strings one a row, bytes in hex, levels and keywords), Recovery (the first, second and subsequent failures' actions, the reset period in days, one restart delay and one reboot delay, the command line, actions for stops with errors; WinSys `Service::GetFailureActions`/`SetFailureActions`). Each page applies what it changed on OK or Apply through a `Service` opened with `SERVICE_CHANGE_CONFIG` (and `SERVICE_START` for a restart action); a failure is reported (with the elevation hint) and keeps the sheet open; the row's cached configuration is loaded again afterwards (`ServiceItem::Reload`). The row menu also has New Service (also on a right-click below the rows; `CServiceInstallDlg`, `ServiceInstallDlg.*`: WinSys `ServiceManager::Install` with the name, display name, binary path (quoted if it has spaces), type, start type, error control, account and password, and dependencies, then the description and, if asked, a start; a driver by default on the Drivers tab; a failure to create keeps the dialog open) and Delete Service (`ServiceManager::Uninstall` after a confirmation; a running service goes once it stops); both refresh the list at once, and a new service is selected. Double-clicking a service, or "Go to Process", calls `IMainFrame::GoToProcess`, which switches tabs and calls `IView::ShowProcess`.
 The view has the same filter box (`CFilterBox`, Ctrl+F): `m_All` keeps every service and `m_Items` (the rows) only the matches, by name, display name, description, process (ID or name) or binary path; with a filter, the rows are chosen again on every refresh, as a service's process may change.
- **Users view** (`UsersView.*`): a TreeListView with a row per session (WinSys `SessionManager`, `<WinSys/Sessions.h>`) and the session's processes as its children, like Task Manager's Users tab; the session rows show totals of their processes (the Idle process is left out). Each refresh enumerates the sessions without details, and gets the details (logon time, client name) only for a new session or one whose state or user changed: those queries raise and handle RPC exceptions (0x6BA) for sessions without a client. New sessions start collapsed (the TreeListView expands a new parent), except the user's own at startup. The filter box (`CFilterBox`, Ctrl+F) keeps the processes whose image name or PID contains its text, or whose session's title, name or client does (`Matches`); only those are in the tree (`SyncProcesses` inserts and deletes them), and the session rows always stay; a filter change refreshes as a tick does. Disconnect and Log Off ask first. Keyboard context menus come as `WM_CONTEXTMENU` with -1, -1; mouse ones as `NM_RCLICK`; the header's `WM_CONTEXTMENU` is told apart by the position. Its columns work like the Processes view's (`m_Columns` maps list columns to `Column`, Name stays list column 0 for the tree; the `UserColumns` setting, View > Select Columns, the header menu; Copy copies the shown columns).
- **Network view** (`NetworkView.*`, the fifth tab, Ctrl+5): every process's connections (WinSys `ConnectionInfo::Read`), read and merged on every tick (`ConnectionRows::Merge`, `ConnectionRows.*`, shared with the TCP/IP page: `ConnectionRow` adds the highlighting to WinSys `Connection`), hidden or not (a few milliseconds), so the highlighting stays right: new ones green, closed ones red once. `m_All` is the merge and `m_Rows` points into it, so the selection's key is taken before a merge and the rows rebuilt after (`ShowRows`). The process column has the process's icon (`IMainFrame::GetProcessIcon`); the filter box (`CFilterBox`) matches the process, PID, protocol, addresses, ports and state; double-click or Go to Process calls `GoToProcess`; Copy copies the selected row's shown columns. Columns work as in the Services view (`ColumnLayout`, the `NetworkColumns` setting, Process mandatory). Sent and Received (and Send Rate and Receive Rate, hidden by default) come from the shared ETW tracker (`NetworkTracking`, so only elevated), held while one of them is shown: WinSys `ProcessNetworkTracker::GetConnectionCounters` per connection (TCP by both ends, UDP by its local port), the bytes since the trace started (the status line says when: `GetStartTime`), as nothing keeps earlier counts; the rates are over the last three refreshes' counts (`ConnectionBytes`, `ConnectionRows.*`, by row key, shared with the TCP/IP page), as the events come in batches about once a second, as the refreshes do, and a rate over one refresh had twice or none of the traffic; the tracker forgets closed connections by itself. UDP sockets of a process sharing a port are counted together: the events give only the process and the ports. Options > Resolve Addresses (`ResolveAddresses`, on by default) shows the addresses, here and on the TCP/IP pages, by their DNS names: `AddressResolver` (`AddressResolver.*`, used from the UI thread and the sheets') looks them up with WinSys `ConnectionInfo::LookupName` on four worker threads of its own and caches every answer (no name too), looked up again once it's an hour old (no name: five minutes), the old answer shown meanwhile, and dropped when not asked for in an hour; until the first answer the address shows, and the window that asked gets `WM_ADDRESS_RESOLVED` (the view repaints, or chooses its rows again while filtered, as the filter matches the names). Unspecified addresses aren't looked up; while names show, the address columns sort by the text. At exit `Shutdown` detaches the workers (a lookup can't be canceled), and the resolver is never destroyed. The row menus (here and on the TCP/IP page, which has one for its selected rows) have Close Connection (WinSys `ConnectionInfo::Close`, after a confirmation; enabled when elevated, for IPv4 TCP connections) and Resolve Again (`AddressResolver::Refresh`). The handlers copy the connections before the confirmation, as refreshes go on while a message box is up and a merge moves the rows (a pointer kept across it crashed). The status line counts the connections (and the filter's matches) while the tab is active.
- **Kernel Modules view** (`KernelModulesView.*`, the sixth tab, Ctrl+6, `atom.ico`; the Drivers tab before the driver services got that name): the kernel's loaded modules from WinSys `KernelModules::Enum`, read and merged on every tick, hidden or not, keyed by path and base: new ones green for two refreshes (not on the first read), unloaded ones red once. The bases need elevation (the status line says so). Description, company and version come from `GetCachedVersionInfo` as they're shown; the signatures are verified by a `SignatureVerifier` (`SignatureVerifier.*`: WinSys `FileSignature` on a `std::jthread`, with a locked map of results shared with the thread, which its owner may outlive), which starts when the tab is first shown (hundreds of files, some through the catalogs) and gets the paths of drivers loaded later, posting `WM_KMODULE_SIGNED` as each is done. The filter box matches the name, path, description and company; double-click or Properties opens the shell's file properties (`SHObjectProperties`); Open File Location and Copy as elsewhere. Columns work as in the Services view (`ColumnLayout`, the `KernelModuleColumns` setting, Name mandatory; while it's empty, the layout saved under the tab's old name, `DriverColumns`, is read).
- **Drivers view** (the seventh tab, Ctrl+7, `Driver.ico`): the driver services (kernel and file system drivers), the Services view's class with `CServicesView::Kind::Drivers`: it enumerates `ServiceEnumType::AllDrivers`, has its own column table (the same columns and keys, no process or account by default) in the `DriverServiceColumns` setting, and gives no delayed start in the row menu's Start Type. `CServiceSheet` tells a driver by its service type (`ServiceSheetData::Driver`) and shows only the General, Dependencies and Security pages, with a driver's start types (Boot and System too, no delayed start): a driver has no account and no recovery actions. The row menu's Start Type has Boot and System for a driver (inserted, with their own IDs, `ID_SERVICE_START_BOOT`/`SYSTEM`) and no delayed start; Go to Process becomes Go to Kernel Module (also on a double-click, enabled while the driver runs). The two tabs are linked by the driver's file: WinSys `KernelModules::DriverImagePath` turns a driver service's image path (`\SystemRoot\...`, `system32\drivers\x.sys`, `\??\...`, or none: `System32\drivers\<name>.sys`) into the Win32 path a loaded module has; `IMainFrame::GoToKernelModule` and `GoToDriver` switch tabs and call `IView::ShowKernelModule`/`ShowDriver` (Kernel Modules' row menu has Go to Driver), clearing a filter that hides the row, and say so if there's none.
- **RPC/ALPC view** (`IpcView.*`, the eighth tab, Ctrl+8, `IDI_ALPC`): which processes talk to which, from WinSys `IpcTracker` (an ETW session, elevated only, so the status line says why it's empty otherwise), started when the tab is first shown and kept until the view goes: ALPC messages per client and server process, and RPC calls per client, interface and endpoint, with the server once a server-side call on the endpoint was seen (calls to other machines show the address). Read and merged on every tick (also while hidden), keyed by `KeyOf` (an RPC row's key leaves the server out, as it may come later): new rows green for two refreshes (not on the first read), the rate over the last refresh. Exited processes are forgotten (`RemoveProcess`), their rows with them. Interface names come from `IpcTracker::GetInterfaceName` (well-known RPC interfaces, else HKCR\Interface), cached per GUID. The filter box matches the processes, PIDs, kind, interface, endpoint and protocol; double-click goes to the server on its columns, else the client; the row menu has Go to Client, Go to Server and Copy. Columns work as in the Network view (`ColumnLayout`, the `IpcColumns` setting, Client mandatory). Only traffic while the session runs shows: an idle connection appears with its first message.
- **Zombie Processes view** (`ZombiesView.*`, the ninth tab, Ctrl+9, `IDI_PROCESS_KILL`): processes that exited but are kept alive by open handles, from WinSys `ZombieProcesses::Find` (elevated, or only the handles of processes it can open; the status line says so). A row per zombie and holder process (a leaking holder has dozens of handles to one zombie), with the holder's handle count, its first four handle values (`ShownHandles`, then the number left) and access; the Zombie and Holder columns have icons (subitem images), the zombie's from its executable through `IMainFrame::GetProcessIcon(path)`, the by-path form of the cached process icons, as a zombie isn't in the snapshot. Scanned on a `std::jthread` (`WM_ZOMBIES_FOUND`) when the tab is shown, every `ScanInterval` (5 s) while it's active, not on every tick, and right after handles are closed; joined in `OnDestroy`. Show All Handles opens `CZombieHandlesDlg` (`ZombieHandlesDlg.*`, modal, resizable, multi-select, on a copy of the row's zombie, as scans go on meanwhile): the zombie's details above every handle keeping it, in all its holders (the row's holder's first and selected), each with its holder (and icon), value, access, the rights decoded (`AccessMaskDecoder`, Process) and the attributes (Inherit, Protect from close, from WinSys `ZombieHolder::Attributes`); Close Selected and Close All close them after a confirmation (`CZombieHandlesDlg::CloseHandle`, the view's too), a closed one grayed and a failure red with its error in the Status column, and the view scans again after the dialog if any was closed; Copy copies the selected rows or all. Close Handles closes the row's handles in the holder and Close All Handles every handle to the zombie (`HandleNames::CloseInProcess`, type Process, after a confirmation); double-click or Go to Holder calls `GoToProcess`. Columns as in the other list tabs (`ColumnLayout`, the `ZombieColumns` setting, Zombie mandatory).
- **Object Types view** (`ObjectTypesView.*`, the tenth tab, Ctrl+0, `IDI_OBJECT`), as ObjectExplorer's: the kernel's object types from WinSys `ObjectTypes::Enum` (one `ObjectTypesInformation` query) with their counts and peaks, pool type and default charges, valid access mask, generic mapping (decoded by `AccessMaskDecoder`) and invalid attributes. Read on every tick, also while hidden; a count that changed since the previous refresh has its cell colored for that refresh (`Row::Change`, subitem custom draw: green up, red down; the other cells get back the colors the list chose for the row at the item stage, never `CLR_DEFAULT`, which is the system's black text even on a dark selection). The icons are the Handles page's (`GetHandleIcon`). The filter matches the name; columns as in the other list tabs (`ObjectTypeColumns`, Name mandatory).
- **Object Manager view** (`ObjectManagerView.*`, the eleventh tab, Ctrl+Shift+O, `IDI_OBJECTS`, `objects.ico`), as WinObj and ObjectExplorer: the object namespace from WinSys `ObjectNamespace`, a `CTreeViewCtrl` of directories (the root inserted when the tab is first shown; a node's subdirectories when it's first expanded, item data 1, `FillNode`; the selected directory's kept in step with its listing, `SyncNode`) beside a `CVirtualListView` list of the selected directory's objects, in a `CCustomSplitterWindow` that forwards both controls' notifications (the tree's handled by its ID, `TreeId`, before the list's handlers). The list is read again on every tick while the tab is active and merged by name: new objects green for two refreshes, removed ones red once; the selection is restored by name without scrolling to it, unless View > Keep Selection Visible (the Processes view's setting) is on (`ShowRows`' `ensureVisible`; a new directory, a filter or a header's sort shows it). Symbolic links' targets and creation times are read once per link; Handles is read for the rows shown (`ObjectNamespace::GetHandleCount`, an object opened by name with no access, else `MAXIMUM_ALLOWED`; only the types `ObjectNamespace::Open` knows: no devices or files), again on every refresh. Double-clicking (posted to the frame, which routes the command to the view) opens a directory, goes to a link's target (`GoToTarget`: its deepest directory in the namespace and the next component's row in it, clearing a filter that hides that row), and opens anything else's properties: `CHandleSheet` on a handle this process opens by name (`MAXIMUM_ALLOWED`, else none; `ObjectNamespace::Describe` makes the `HandleEntry`; `SetSheetTitle` names the object rather than the handle, and `HideHandle` leaves out the handle's value and attributes, as the handle is the app's own, and that handle from the counts); the tree's context menu has the directory's Properties and Copy Path. Icons are the Handles page's (`GetHandleIcon`; `SymbolicLink` has `IDI_SYMLINK`), devices `IDI_DEVICE` and drivers `IDI_DRIVER`. The filter box matches the name, type and target. Rows are by name until a header is clicked. Settings: `ObjectManagerColumns` (Name mandatory), `ObjectManagerPath` (reopened at startup, as much of it as is still there) and `ObjectManagerSplitterPos`.
- **Pool Tags view** (`PoolTagsView.*`, the twelfth tab, Ctrl+Shift+P, `IDI_POOLTAGS`, `PoolTags.ico`), as PoolMonX: the kernel pools' usage by tag from WinSys `SystemInfo::GetPoolTagInformation` (one query), with paged and non-paged allocations, frees, their difference and the bytes in use, a total (hidden by default), and each tag's binary and description from WinSys `PoolTagDescriptions`: the Debugging Tools' `pooltag.txt` if installed (`FindFile`), else the copy built into the app (`IDR_POOLTAGS`, `res\pooltag.txt`, RCDATA); the status line says which. Non-elevated, the query succeeds with a single placeholder (tag `None`, every counter zero), which the view recognizes (`m_Withheld`): no rows, and the status line says elevation is needed. Read on every tick while the tab is active (also when it's activated, then without change marks, as it isn't read while hidden); a counter that changed since the previous refresh has its cell colored for that refresh, as on the Object Types tab. The filter matches the tag, binary and description; columns as in the other list tabs (`PoolTagColumns`, Tag mandatory).
- **Disk view** (`DiskView.*`, the thirteenth tab, Ctrl+Shift+D, `IDI_HARDDISK`, `Harddisk.ico`): file I/O per process and file from WinSys `FileIoTracker` (an ETW session on Microsoft-Windows-Kernel-File, elevated only, so the status line says why it's empty otherwise), started when the tab is first shown and kept until the view goes, as the RPC/ALPC tab's. Read and merged on every tick (also while hidden, for the rates), keyed by PID and file key: new rows green for two refreshes (not on the first read), rows the tracker forgot (a minute without I/O, or `RemoveProcess` for an exited process) red once. The rates are over the last three refreshes' counts (`RateUpdates`, a `History` per row), as the Network tab's, the events coming in batches about once a second. Until a header is clicked the rows are by PID and file key, as the tracker's order is a hash table's. A file the tracker couldn't name shows its file key (`(file 0x...)`): mostly System's lazy writes and paging I/O, whose file objects no process has a handle to. The filter box matches the process, PID and file; double-click or Go to Process calls `GoToProcess`; File Properties and Open File Location need a DOS path; Copy copies the shown columns. Columns as in the other list tabs (`DiskColumns`, Process mandatory).
- **History view** (`HistoryView.*`, the fourteenth tab, Ctrl+Shift+H, `IDI_HISTORY`, `History.ico`): a log, in a wtlhelper `CLogViewCtrl` with its toolbar (filter, search, level buttons, follow), of processes started and exited and services started, stopped (a failure, with its exit code, as a warning and \"Service failed\"), paused, resumed, installed and deleted, while the tab exists (also hidden: every view gets `OnRefresh`). Processes come from the frame's snapshot (`GetNewProcesses`, `GetTerminatedProcesses`): a start at the process's creation time with parent, user and command line, an exit with how long it ran and its exit code (WinSys `Process::GetExitCode`, through a handle opened, query limited and synchronize, when the process was first seen, as an exited process can't be opened by ID); a non-zero exit code is a warning. Services are enumerated on every refresh while one of their kinds is on and compared by name with the last enumeration; pending states are waited out. What's there when the tab opens is the baseline (`TakeBaseline`): its processes' first appearance as new isn't a start. Each line is `yyyy-MM-dd hh:mm:ss.fff  <label>  <text>`, with its kind's gutter marker (styles 1.., `s_Markers`), level info or warning, and the PID as its `lParam` (Go to Process, also on a double-click, for a process still running); a refresh's lines are sorted by time before they're appended. The log's context menu (`LGVN_CONTEXTMENU`) has Go to Process, Copy, Select All, Save Log (also File > Export List, Ctrl+S: the view handles `ID_FILE_EXPORT` itself, `IView::CanExport` enabling it, and writes the lines the log's filter shows, read before the dialog, to a UTF-8 text file, `ListExport::Save`), Events (the six kinds, the `HistoryEvents` setting, `1 << CHistoryView::Event`) and Clear; Ctrl+F focuses the log's search box (the second edit of its toolbar), and the toolbar's Copy copies the selection or the caret's line. At most 100,000 lines. The status line counts the events and names the kinds on.
- **Autoruns view** (`AutorunsView.*`, the fifteenth tab, Ctrl+Shift+A, `IDI_AUTORUNS`, `autoruns.ico`; entries without an icon of their own get `IDI_RUN_COMMAND`), as Sysinternals' Autoruns: what starts by itself, from WinSys `Autoruns::Enum` (Run and RunOnce keys, startup folders, Active Setup, scheduled tasks, auto-start services and drivers, Winlogon, AppInit, BootExecute, LSA packages, IFEO Debugger and SilentProcessExit values; about 600 entries in under a second). Scanned on a `std::jthread` (COM initialized on it; `WM_AUTORUNS_SCANNED`, joined in `OnDestroy`) when the tab is first shown, when it's activated a minute or more after the last scan (`RescanAge`) and on Scan Again, not on refresh ticks (F5 reaches every view's `OnRefresh` like a tick, so it can't be told apart). Signatures as in Kernel Modules (`SignatureVerifier`, `WM_AUTORUNS_SIGNED`); Hide Microsoft Entries (the `AutorunsHideMicrosoft` setting, on by default; in the row menu and the empty area's) leaves out entries whose image has a valid signature with "Microsoft" in the signer, shown until verified, so the rows are chosen again as results arrive; the status line counts them. A row's leftmost column has the program's icon for an .exe (`GetProcessIcon(path)`), else its category's. An image that isn't there is highlighted yellow ("File not found: ..."; a task's unregistered COM handler says so), a disabled entry grayed. The row menu: Enabled (Run keys with a StartupApproved key, startup items and tasks; `Autoruns::SetEnabled`, the row updated in place), Delete (Run values, startup files, tasks and hijack values, after a confirmation that says what goes; `Autoruns::Delete`), Jump to Entry (Regedit at the key, through its `LastKey` value and `-m`; Explorer at a startup file; the Task Scheduler, which can't be opened on a task, the path in the status line), Properties (also a double-click) and Open File Location for the image, VirusTotal, Copy; failures are reported with the elevation hint. The filter box matches the entry, category, paths, command, location, description, company and details. Columns as in the other list tabs (`AutorunsColumns`, Entry mandatory; the tasks' state, triggers, runs, result, account and author hidden by default). A toolbar right of the filter in the view's rebar (`m_Bar`, `ToolbarHelper::CreateAndInitToolBar`, as the Processes view's Hide button: no grippers, the filter's band keeping its width and `UpdateLayout` maximizing the bar's; icons and font again on a DPI change, `LayoutBar`) has Hide Microsoft Entries (checked while on) and Scan Again (disabled while scanning; `UpdateBar`); their commands come to the view itself through the rebar, so its main message map handles them as well as `ALT_MSG_MAP(1)`.
- **Performance view** (`PerfView.*`, `PerfNav.*`, `PerfPages.*`): a list of pages on the left (`CPerfNav`, a custom-drawn window with a small history graph for each resource, which scrolls when the items don't fit; Up, Down, Page Up, Page Down, Home and End move the selection) and the selected page on the right. Summary shows CPU, memory, network and total disk transfer, in a 2×2 grid when the page is wide enough. The selected page is saved by name in the `PerfPageKey` setting (`PageKey`: "CPU", "Disk:C", "GPU:0"...), as the drive and GPU pages' indices shift when drives come and go; the older `PerfPage` index is read only when there's no name yet.
  - `CPerfView` takes one `PerfSample` per refresh tick from WinSys `SystemInfo` (per-processor times queried for each processor group, plus performance, basic and memory list information) and hands it to **every** page, also hidden ones, so their graphs have history when shown.
  - Pages implement `IPerfPage` through the `CPerfPage<T>` base (background, text lines below the graphs, layout): Summary, CPU, Memory, Network, I/O (`CPerfIoPage`: the system's read, write and other transfer rates and operations per second, all processes' I/O, from `SYSTEM_PERFORMANCE_INFORMATION`'s counters, which `CPerfView::SampleIo` turns into rates over QPC time; its key is "IO"), one per drive, one per GPU and one per NPU. To add one, add the data to `PerfSample`, write the page class, and add a nav item and a `m_Pages` entry in the same order (`NavItem`).
  - Graphs are GraphControl's `CGraphControl`, `CGraphGrid` and `CCompositionBar` from wtlhelper, included as `<GraphControl/include/...>`. Each graph keeps its own history, so a graph shown on two pages is two controls fed the same sample.
  - Network data comes from WinSys `NetworkTracker` (`<WinSys/Network.h>`, `GetIfTable2`, about 4 ms per tick), owned by the view; the sample points to its interface list. The Network page graphs only adapters that are up, and creates or destroys their graphs as that set changes.
  - Drive pages come from WinSys `DiskTracker` (`<WinSys/Disk.h>`). They're dynamic: `SyncDiskPages` inserts and removes pages and nav items, in drive letter order from `FirstDiskItem`, when drives appear or disappear. That's why the view keeps `m_Theme` and `m_TimeSpanText`, which pages created later need.
  - GPU pages (`CPerfGpuPage`) come from WinSys `Gpu.h`: `GpuInfo::GetAdapters` reads the adapters once (`D3DKMTEnumAdapters2`, software and non-rendering ones left out, names from DXGI, engine names from `KMTQAITYPE_NODEMETADATA`, grouped by name; aperture segments are shared memory), and `GpuTracker` samples the nodes' running times (100 ns units, whatever the header says) and the segments' resident bytes. An engine's utilization is its busiest node's, an adapter's its busiest engine's (as Task Manager). The pages follow the drive pages (`FirstGpuItem`), so they move as drives come and go; each has a grid of engine graphs and the dedicated and shared memory graphs.
  - NPU pages are GPU pages (`CPerfGpuPage` with `GpuAdapterKind::Npu`, their adapters and samples from a second `GpuTracker`), after the GPU pages (`FirstNpuItem`, keys "NPU:0"...).
  - All pages are kept sized, not just the visible one, because laying out the per-processor grid is slow. The CPU page sets the grid's layout from its aspect ratio, because the grid's automatic layout is square.
  - CPU details (`CPerfView::SampleCpu`): per processor, `SYSTEM_PROCESSOR_PERFORMANCE_INFORMATION`'s DPC and interrupt times and interrupt count, and `SystemInterruptInformation`'s DPC count (`CpuTimes`); the kernel time already includes DPC and interrupt time (measured: kernel and user time alone make up the elapsed time), so `PerfSample::InterruptCpu` and `DpcCpu` are parts of `KernelCpu`, with the rates per second. The CPU page's graph is `CCpuGraph` with `details` (stacked: Interrupts, DPCs, the rest of kernel time, User; the Summary's has Kernel and User). Each tile of the per-processor grid has its processor's frequency in its title (WinSys `ProcessorFrequency`, opened by the view, read on every tick: PDH's Processor Frequency times % Processor Performance, as Task Manager's Speed; `CoreMhz`, `BaseMhz`), and the text block has the average, the fastest and the rated speed, the interrupt and DPC shares and rates, and the cores (`m_CoresText`, from WinSys `SystemInfo::GetLogicalProcessorCores`). On a hybrid processor (the cores' efficiency classes differ), `InitCoreKinds` tags each tile's title with its core's kind (`m_CoreKinds`: P for the highest class, LP-E for the lowest of three or more, else E; `TileTitle`), tints the E-cores' tiles teal (GraphControl `CGraphGrid::SetTileSeriesStyle`) and counts the cores of each kind. Every sample carries the five busiest processes (`TopProcesses`, from the frame's snapshot, Idle left out); `CCpuGraph` keeps them per sample with the time it was pushed, and the CPU and Summary pages answer the graph's `GCN_GETTOOLTIP` with `TooltipText`: the readout and the processes of the sample nearest the hovered one's time (`GetSampleAgeSeconds`, as the graph fills missed intervals with gaps), names cut to fit the readout's 255 characters.
  - The CPU page's Show processors check box (at the end of the text block; the `PerfShowProcessors` setting) hides the per-processor grid, the CPU graph then taking its place; hidden, the grid still takes the samples. - **Devices view** (`DevicesView.*`, the sixteenth tab, Ctrl+Shift+E, `IDI_DEVICE`): the device tree as Device Manager shows it, from WinSys `Devices::Enum`, in a TreeListView. - **Events view** (`EventsView.*`, the seventeenth tab, Ctrl+Shift+L, `IDI_EVENT`): the chosen logs' events of the chosen time span (at most 5,000 a log, 15,000 in all, so the Security log's audits can't push the others out; newest first) from WinSys `EventLog::Query`, the logs merged by time, read on a `std::jthread` (`WM_EVENTS_READ`) when the tab opens and on Refresh; then the new ones as they're written, from an `EventLogWatcher` the view is the sink of (`EventLogSink::OnEvent` on wevtapi's threads queues them under `m_Lock` and posts `WM_EVENTS_NEW` once per burst; added at the top unless already read, by log and record ID; the selection kept by that key, as `m_All` grows; `Stop` in `WM_DESTROY` waits for a callback in progress). Errors and critical events always; the toolbar's Warnings (the system's `IDI_WARNING`, through WTLHelper's `IconId`; on at first; with them the Security log's audit failures) and Information (off; with it the audit successes, by far the most events: 4688, a process created, alone fills the 5,000) set the highest level read and watched, and two drop-downs (`BTNS_WHOLEDROPDOWN`, `TBSTYLE_EX_DRAWDDARROWS`, `TBN_DROPDOWN` through the rebar; their menus' items are returned, `TPM_RETURNCMD`, not commands): Logs, a checklist of System, Application, Security, Setup, Windows PowerShell, Microsoft-Windows-PowerShell/Operational, Defender's, Task Scheduler's and Sysmon's operational logs, those that exist (WinSys `EventLog::Exists`) or are chosen (at least one stays), and the time span (Last Hour, 24 Hours, 7 Days, 30 Days, its text the button's); the Security log needs elevation (without it the status line says so; the watcher keeps the other logs); all saved (`EventsWarnings`, `EventsInformation`, `EventsLogs` separated by `|`, `EventsHours`; an empty `EventsLogs` is System and Application, and Security unless the older `EventsSecurity` was off); changing one restarts the watcher and reads again (`Included` checks a live event against them, by its audit keywords for level 0); Refresh. The Security log's events are level 0 and told by their keywords: their level shows as Audit Failure (orange background) or Audit Success, with `IDI_KEY`, and sorts by severity (critical, error, audit failure, warning, information, audit success, verbose); the status line counts the audit failures. A log that can't be read is named in the status line with the error. A `CVirtualListView` (`EventColumns`; the usual header menu): time, level (the system's stock `IDI_ERROR`, `IDI_WARNING` and `IDI_INFORMATION`, as Event Viewer's, in the frame's `s_SystemIcons`: one missing there would get no icon; `IDI_KEY` for audits), log, source, event ID, process (the logging process's name from the frame's snapshot, only while it runs and was created before the event: its ID may be another's since; System for 4), PID, message (its first line). Details: the event's data fields summarized (`EventAlertText::Summarize`, as the alerts' text: "C:\Windows\System32\cmd.exe created by ZODIAC\zodia, parent ..." for 4688), for the Security log's events and those without a message; read with the events (`EventLog::Query` with `EventDataRead::All` for Security and `NoMessage` for the other logs, about 15 µs an event, 70 ms more for 5,000; the watcher with its data) and condensed on the reading threads to that one text (`CEventsView::Condense`: kept as the event's only data item, the fields dropped; a summary that only repeats the message's line is dropped, and the line's "(fields)" form keeps the fields alone).
