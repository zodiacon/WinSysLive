# The other tabs

Each tab but Processes (see [processes-view.md](processes-view.md)), in detail. Read the tab's entry before changing it.

- **Threads view** (`ThreadsView.*`, View > Threads, Ctrl+Shift+T, `IDI_THREADS`, listed right after Processes in the View menu, `s_Tabs` and the toolbar; `TabType::Threads`, the `Threads` key; columns in the `ThreadsViewColumns` setting): every thread of every process (10,475 in 566 processes here), from the frame's snapshot (each process entry's `SYSTEM_EXTENDED_THREAD_INFORMATION` array), in an owner-data list with the Threads page's columns (`CThreadsPage`) and the process (its icon from the frame, a subitem image) and PID; the state's icon in the leftmost column, new threads green and exited ones red for the highlight durations, as on the page. Shown at first: Process, PID, TID, CPU, CPU Time, State, Wait Reason, Priority, Base Pri, Ctx Switch Delta, Service, Start Address, Created; the rest (Kernel and User Time, Cycles and Cycles Delta, Ideal CPU, I/O and Memory Pri, Ctx Switches, COM Apartment, CPU History) can be added. CPU History (`CpuHistory.h`) is a sparkline per row from GraphControl's `CellGraphs`, drawn from the custom draw: a series in the row's `ThreadState` (an `optional`, made only while the column is shown, as there are thousands of threads), pushed on every refresh taken (the first after the tab is shown again is a gap: its CPU isn't known), a process row's (Group by Process) from its threads' total, pushed once a refresh after `ShowRows` (which filtering calls again); the column's text, sorting and filtering are the CPU's. A thread's samples are percents of one processor (`CpuHistory::Scale::Processor`: a thread always running is at 100%, in the graph and its tooltip; as a percent of the machine, a busy thread on 32 processors was a flat line at 3%), a process row's its threads' total as a percent of the machine (`Scale::Machine`, as the Processes tab's CPU History); both graphs are 0-100 (tested: `Threads_CpuHistoryScale`). With sub-item drawing on, the rows' colors are set at the sub-item stage too. Taken only while the tab is active (an inactive tab isn't seen; `OnActivate` forgets the rates, which start again: CPU and the deltas are empty for the first refresh). Measured with the tab active: 5% of a core in Release against 4.1% for the Processes tab, handles unchanged. Per thread a `ThreadState` (`std::unique_ptr`s in `m_States` and, for the exited ones still shown, `m_Exited`, so a row's pointer to it survives the move); the Idle process's threads (one a processor, three on this build: TID 0 and two more, all created at 0) are keyed by their index (`Created` = -(index + 1)), as their keys collided (rows pointed at states dropped as duplicates: wrong process names and a core's worth of CPU, until fixed). What a handle gives (cycles, ideal CPU, the I/O and memory priority, the service by its tag, the start address when the snapshot has none, the COM apartment through the TEB and a process handle per process, `ProcessState`) is read by `Read` only for the rows painted and at most once a refresh (`ReadRefresh`), every row's when sorting by such a column (not Start Address, sorted by the address, nor COM Apartment); Cycles Delta is known for a row read on consecutive refreshes. Handles open when first needed and close after `HandleIdle` (60 s) unused, as an open handle keeps an exited thread's object alive. Implicit MTA reads all of the process's threads' flags (`HasMta`, `m_ByProcess`, built while COM Apartment is shown). The filter matches the process, PID, TID, state, wait reason and a service already known, never querying (a symbol lookup for every thread would load every process's symbols); the start addresses' symbols are looked up for the rows painted (`WM_SYMBOLS_RESOLVED` repaints). Sorting breaks ties by PID and TID. A row's menu is the Threads page's (`ThreadCommands`) with Go to Process (`ID_THREADS_GOTOPROCESS`) first; the double-click shows the stack; Kill (Del, the toolbar; enabled through `OnFrameIdle`) terminates the selected thread after asking. Export and Copy All take the list (so every row's handle values and symbols are read). Hide Idle Threads and Hide Idle Process (`ID_THREADS_HIDEIDLE`, `ID_THREADS_HIDEIDLEPROCESS`: check buttons in a toolbar beside the filter, as the Users tab's Group by Account, and View menu items, so the command palette has them, enabled while the tab is active; the `ThreadsHideIdle` and `ThreadsHideIdleProcess` settings, off and on at first) hide the threads that used no CPU and made no context switch since the last refresh (`IsIdle`: the CPU time and context switch deltas both 0; not known on the first refresh: shown; new and exited threads always show, for their highlights) and the Idle process's threads (72 here). With both on here: 651 of 10,870 threads shown. Group by Process (`ID_THREADS_GROUPBYPROCESS`, a third check button beside them and View > Group Threads by Process; the `ThreadsGroupByProcess` setting, off at first) puts a row for each process above its threads (`BuildGroups`: `m_Groups`, their threads in `m_GroupThreads`, their order in `m_GroupOrder`, flattened into `m_Rows` by `Flatten`), tinted, its leftmost column with a ▸ or ▾ (as `\u25B8`/`\u25BE` escapes: the source is read in the ANSI code page) and its threads' indented, its name with the count of threads it shows, and their totals: CPU, CPU, Kernel and User Time, Ctx Switches and Ctx Switch Delta (the other columns empty; Created is the process's). A process row's key is the process's with `GroupBit` in the ID, so the selection (kept by key) can't take it for a thread; its names and icon come from a `ThreadState` of its own (`m_GroupStates`). Processes start collapsed; the double-click, Enter, Right and Left (`LVN_KEYDOWN`; Left on a thread goes to its process's row), the row's menu (Expand or Collapse, `ID_THREADS_TOGGLEGROUP`; Expand All, Collapse All, `ID_THREADS_EXPANDALL`, `ID_THREADS_COLLAPSEALL`; Go to Process; Copy) expand them (`m_Expanded`, by process key; the processes gone forgotten each refresh); while the filter has text every process shows its threads that match. Sorting sorts the process rows by the column (their totals, or their texts), and each process's threads the same way (`SortRows`, `DoSort`). The thread commands, Kill and the double-click's stack leave process rows alone. The status line counts the threads and processes, those hidden (and by which option) and those shown, and, grouped, the processes shown and expanded.
- **Services view** (`ServicesView.*`; also the Drivers tab, see below) is a plain owner-data list view built on `CVirtualListView` and `ColumnManager`, the TotalPE pattern. On each refresh it enumerates services again and merges the result by name. Each service's configuration and description cost a call to the Service Control Manager, so they're loaded on first display and cached (`ServiceItem::GetConfig`). Selection is restored by service name: `GetSaveColumnRange` returns -1 to turn off `CVirtualListView`'s own restore. Stop and Restart take the running dependents along (WinSys `Service::GetDependents`, after a confirmation that lists them): they're stopped first, in the SCM's order, then the service; a restart then starts the service and the dependents that ran, in the reverse order. `ServiceControlSteps` (`ServiceSteps.*`, also the process sheet's Services page's Stop) sends one control at a time, and the view polls it with a timer (each service waited for up to 30 s) rather than blocking; a stop that fails or times out ends the steps, and the starts that failed are reported at the end. Columns work as in the Processes view (`ColumnLayout`, the `ServiceColumns` setting; Name and State are mandatory): `SetColumns` rebuilds the `ColumnManager` with only the shown columns, in display order, which clears the sorting. The header's right-click arrives as `WM_CONTEXTMENU` from the list view (its `NM_RCLICK` never reaches `CVirtualListView`), so it's told apart from a row's by the position. Required privileges and triggers are loaded on first display and cached like the configuration; the Triggers column shows each trigger's type and action, those alike counted (WinSys `Service::GetTriggerDetails`; the subtypes and data are on the sheet's Triggers page). The row menu also has Start Type (Automatic, Automatic (Delayed Start), Manual, Disabled, the current one checked; WinSys `Service::ChangeConfig` and `SetDelayedAutoStart`) and Properties (Alt+Enter, enabled from the view's `OnFrameIdle`; the Processes view updates that command only while it's active): `CServiceSheet` (`ServiceSheet.*`), modal, as services.msc has it: General (display name, description, path, start type, error control), Log On (Local System, Local Service, Network Service or an account with its password, which stays unless typed again; read-only for a per-user service) Dependencies (`CServiceDependenciesPage`, for drivers too: two trees, what the service depends on, services and load order groups, and the services depending on it directly, sorted; a node gets its children when expanded, the direct dependents picked from `GetDependents`, which lists indirect ones too, by their configured dependencies, a load order group to its services (every service's group read once, on the first group expanded); double-clicking a service or its context menu opens its sheet, hit-testing the cursor's position), Security (the ACL editor's page on a `CServiceSecurityInfo`, `ObjectSecurity.*`: a `CObjectSecurityInfo` whose descriptor goes through WinSys `Service::GetSecurity`/`SetSecurity`, as the SCM's objects aren't kernel objects, with a service's rights and generic mapping; opened with the most of READ_CONTROL, WRITE_DAC and WRITE_OWNER it allows; the sheet installs `CAclDialogTheming`) and Triggers (`CServiceTriggersPage`, added only for a service with triggers: WinSys `Service::GetTriggerDetails`; each trigger's action, type and subtype, named for the documented subtype GUIDs (copied: `INITGUID` is off) and an ETW provider's registered name (`Service::GetEventProviderName`), and the selected one's data items below: a string item's strings one a row, bytes in hex, levels and keywords), Recovery (the first, second and subsequent failures' actions, the reset period in days, one restart delay and one reboot delay, the command line, actions for stops with errors; WinSys `Service::GetFailureActions`/`SetFailureActions`). Each page applies what it changed on OK or Apply through a `Service` opened with `SERVICE_CHANGE_CONFIG` (and `SERVICE_START` for a restart action); a failure is reported (with the elevation hint) and keeps the sheet open; the row's cached configuration is loaded again afterwards (`ServiceItem::Reload`). The row menu also has New Service (also on a right-click below the rows; `CServiceInstallDlg`, `ServiceInstallDlg.*`: WinSys `ServiceManager::Install` with the name, display name, binary path (quoted if it has spaces), type, start type, error control, account and password, and dependencies, then the description and, if asked, a start; a driver by default on the Drivers tab; a failure to create keeps the dialog open) and Delete Service (`ServiceManager::Uninstall` after a confirmation; a running service goes once it stops); both refresh the list at once, and a new service is selected. Double-clicking a service, or "Go to Process", calls `IMainFrame::GoToProcess`, which switches tabs and calls `IView::ShowProcess`.
 The view has the same filter box (`CFilterBox`, Ctrl+F): `m_All` keeps every service and `m_Items` (the rows) only the matches, by name, display name, description, process (ID or name) or binary path; with a filter, the rows are chosen again on every refresh, as a service's process may change.
- **Users view** (`UsersView.*`): a TreeListView with a row per session (WinSys `SessionManager`, `<WinSys/Sessions.h>`) and the session's processes as its children, like Task Manager's Users tab; the session rows show totals of their processes (the Idle process is left out). Each refresh enumerates the sessions without details, and gets the details (logon time, client name) only for a new session or one whose state or user changed: those queries raise and handle RPC exceptions (0x6BA) for sessions without a client. New sessions start collapsed (the TreeListView expands a new parent), except the user's own at startup. The filter box (`CFilterBox`, Ctrl+F) keeps the processes whose image name or PID contains its text, or whose session's title, name or client does (`Matches`); only those are in the tree (`SyncProcesses` inserts and deletes them), and the session rows always stay; a filter change refreshes as a tick does. Group by Account (a check button with text beside the filter, laid out as the Processes view's Hide button: its own toolbar in the next rebar band, which takes the row's extra width; the `UsersGroupByAccount` setting; also View > Group Users by Account, routed to the view's `ALT_MSG_MAP(1)` and so in the command palette, which the frame disables at startup and the view enables and checks while active) groups the processes by the account they run as (`ProcessInfoEx::GetUser`, read once per process, "(Unknown)" for those that can't be opened) instead of by session: Run As starts another user's process in the caller's session, so it has no session of its own. An account row has the totals, and its processes' sessions in Session ID ("0, 1"), which the process rows then show too; accounts come with their first process and go with their last. Switching rebuilds the tree (`Rebuild`; the sessions keep their details) and expands the user's own group. Under each account are its logon sessions (the token's `AuthenticationId`, `ProcessInfoEx::GetLogonId`, read once per process), named by their type and ID ("Interactive logon (0x3A5F21)"; an elevated and a limited token of one user are two; "(Unknown logon)" when the token can't be opened), with totals, sessions and the logon time; their details come from WinSys `LsaSecurity::GetLogonSessionData` once per logon ID (`m_LogonDetails`, dropped when no process has it; another user's need elevation), and they start expanded under their collapsed account. The User, Logon ID and Logon Type columns (table version 1: User is added to saved layouts once, the other two are off by default) give each process's account and logon, in both modes. A process running as a user other than its session's (Run As; not the system and service accounts that run in users' sessions: NT AUTHORITY, NT SERVICE, Window Manager, Font Driver Host...) is drawn in orange (`IsOtherUser`, the tree's `NM_CUSTOMDRAW`). The filter also matches a process's account, in both modes. Disconnect and Log Off ask first (sessions only). Keyboard context menus come as `WM_CONTEXTMENU` with -1, -1; mouse ones as `NM_RCLICK`; the header's `WM_CONTEXTMENU` is told apart by the position. Its columns work like the Processes view's (`m_Columns` maps list columns to `Column`, Name stays list column 0 for the tree; the `UserColumns` setting, View > Select Columns, the header menu; Copy copies the shown columns).
- **Network view** (`NetworkView.*`, the fifth tab, Ctrl+5): every process's connections (WinSys `ConnectionInfo::Read`), read and merged on every tick (`ConnectionRows::Merge`, `ConnectionRows.*`, shared with the TCP/IP page: `ConnectionRow` adds the highlighting to WinSys `Connection`), hidden or not (a few milliseconds), so the highlighting stays right: new ones green, closed ones red once. `m_All` is the merge and `m_Rows` points into it, so the selection's key is taken before a merge and the rows rebuilt after (`ShowRows`). The process column has the process's icon (`IMainFrame::GetProcessIcon`); the filter box (`CFilterBox`) matches the process, PID, protocol, addresses, ports and state; double-click or Go to Process calls `GoToProcess`; Copy copies the selected row's shown columns. Columns work as in the Services view (`ColumnLayout`, the `NetworkColumns` setting, Process mandatory). Sent and Received (and Send Rate and Receive Rate, hidden by default) come from the shared ETW tracker (`NetworkTracking`, so only elevated), held while one of them is shown: WinSys `ProcessNetworkTracker::GetConnectionCounters` per connection (TCP by both ends, UDP by its local port), the bytes since the trace started (the status line says when: `GetStartTime`), as nothing keeps earlier counts; the rates are over the last three refreshes' counts (`ConnectionBytes`, `ConnectionRows.*`, by row key, shared with the TCP/IP page), as the events come in batches about once a second, as the refreshes do, and a rate over one refresh had twice or none of the traffic; the tracker forgets closed connections by itself. UDP sockets of a process sharing a port are counted together: the events give only the process and the ports. Options > Resolve Addresses (`ResolveAddresses`, on by default) shows the addresses, here and on the TCP/IP pages, by their DNS names: `AddressResolver` (`AddressResolver.*`, used from the UI thread and the sheets') looks them up with WinSys `ConnectionInfo::LookupName` on four worker threads of its own and caches every answer (no name too), looked up again once it's an hour old (no name: five minutes), the old answer shown meanwhile, and dropped when not asked for in an hour; until the first answer the address shows, and the window that asked gets `WM_ADDRESS_RESOLVED` (the view repaints, or chooses its rows again while filtered, as the filter matches the names). Unspecified addresses aren't looked up; while names show, the address columns sort by the text. At exit `Shutdown` detaches the workers (a lookup can't be canceled), and the resolver is never destroyed. The row menus (here and on the TCP/IP page, which has one for its selected rows) have Close Connection (WinSys `ConnectionInfo::Close`, after a confirmation; enabled when elevated, for IPv4 TCP connections) and Resolve Again (`AddressResolver::Refresh`). The handlers copy the connections before the confirmation, as refreshes go on while a message box is up and a merge moves the rows (a pointer kept across it crashed). The status line counts the connections (and the filter's matches) while the tab is active.
- **Kernel Modules view** (`KernelModulesView.*`, the sixth tab, Ctrl+6, `atom.ico`; the Drivers tab before the driver services got that name): the kernel's loaded modules from WinSys `KernelModules::Enum`, read and merged on every tick, hidden or not, keyed by path and base: new ones green for two refreshes (not on the first read), unloaded ones red once. The bases need elevation (the status line says so). Description, company and version come from `GetCachedVersionInfo` as they're shown; the signatures are verified by a `SignatureVerifier` (`SignatureVerifier.*`: WinSys `FileSignature` on a `std::jthread`, with a locked map of results shared with the thread, which its owner may outlive), which starts when the tab is first shown (hundreds of files, some through the catalogs) and gets the paths of drivers loaded later, posting `WM_KMODULE_SIGNED` as each is done. The filter box matches the name, path, description and company; double-click or Properties opens the shell's file properties (`SHObjectProperties`); Open File Location and Copy as elsewhere. Columns work as in the Services view (`ColumnLayout`, the `KernelModuleColumns` setting, Name mandatory; while it's empty, the layout saved under the tab's old name, `DriverColumns`, is read).
- **Drivers view** (the seventh tab, Ctrl+7, `Driver.ico`): the driver services (kernel and file system drivers), the Services view's class with `CServicesView::Kind::Drivers`: it enumerates `ServiceEnumType::AllDrivers`, has its own column table (the same columns and keys, no process or account by default) in the `DriverServiceColumns` setting, and gives no delayed start in the row menu's Start Type. `CServiceSheet` tells a driver by its service type (`ServiceSheetData::Driver`) and shows only the General, Dependencies and Security pages, with a driver's start types (Boot and System too, no delayed start): a driver has no account and no recovery actions. The row menu's Start Type has Boot and System for a driver (inserted, with their own IDs, `ID_SERVICE_START_BOOT`/`SYSTEM`) and no delayed start; Go to Process becomes Go to Kernel Module (also on a double-click, enabled while the driver runs). The two tabs are linked by the driver's file: WinSys `KernelModules::DriverImagePath` turns a driver service's image path (`\SystemRoot\...`, `system32\drivers\x.sys`, `\??\...`, or none: `System32\drivers\<name>.sys`) into the Win32 path a loaded module has; `IMainFrame::GoToKernelModule` and `GoToDriver` switch tabs and call `IView::ShowKernelModule`/`ShowDriver` (Kernel Modules' row menu has Go to Driver), clearing a filter that hides the row, and say so if there's none.
- **RPC/ALPC view** (`IpcView.*`, the eighth tab, Ctrl+8, `IDI_ALPC`; COM calls, `IpcTracker::IsComCall`, have COM as their Kind and are counted in the status line, and the COM Server column has the server process's `ProcessInfoEx::GetComServer`, for ALPC rows too): which processes talk to which, from WinSys `IpcTracker` (an ETW session, elevated only, so the status line says why it's empty otherwise), acquired when the tab is first shown (`Recorders::AcquireIpc`, shared: with Record from Startup the frame's, running since the app started) and held until the view goes: ALPC messages per client and server process, and RPC calls per client, interface and endpoint, with the server once a server-side call on the endpoint was seen (calls to other machines show the address). Read and merged on every tick (also while hidden), keyed by `KeyOf` (an RPC row's key leaves the server out, as it may come later): new rows green for two refreshes (not on the first read), the rate over the last refresh. Exited processes are forgotten (`RemoveProcess`, called by the frame for every shared tracker in `Recorders::OnRefresh`), their rows with them. Interface names come from `IpcTracker::GetInterfaceName` (well-known RPC interfaces, else HKCR\Interface), cached per GUID. The filter box matches the processes, PIDs, kind, interface, endpoint and protocol; double-click goes to the server on its columns, else the client; the row menu has Go to Client, Go to Server and Copy. Columns work as in the Network view (`ColumnLayout`, the `IpcColumns` setting, Client mandatory). Only traffic while the session runs shows: an idle connection appears with its first message.
- **Zombie Processes view** (`ZombiesView.*`, the ninth tab, Ctrl+9, `IDI_PROCESS_KILL`): processes that exited but are kept alive by open handles, from WinSys `ZombieProcesses::Find` (elevated, or only the handles of processes it can open; the status line says so). A row per zombie and holder process (a leaking holder has dozens of handles to one zombie), with the holder's handle count, its first four handle values (`ShownHandles`, then the number left) and access; the Zombie and Holder columns have icons (subitem images), the zombie's from its executable through `IMainFrame::GetProcessIcon(path)`, the by-path form of the cached process icons, as a zombie isn't in the snapshot. Scanned on a `std::jthread` (`WM_ZOMBIES_FOUND`) when the tab is shown, every `ScanInterval` (5 s) while it's active, not on every tick, and right after handles are closed; joined in `OnDestroy`. Show All Handles opens `CZombieHandlesDlg` (`ZombieHandlesDlg.*`, modal, resizable, multi-select, on a copy of the row's zombie, as scans go on meanwhile): the zombie's details above every handle keeping it, in all its holders (the row's holder's first and selected), each with its holder (and icon), value, access, the rights decoded (`AccessMaskDecoder`, Process) and the attributes (Inherit, Protect from close, from WinSys `ZombieHolder::Attributes`); Close Selected and Close All close them after a confirmation (`CZombieHandlesDlg::CloseHandle`, the view's too), a closed one grayed and a failure red with its error in the Status column, and the view scans again after the dialog if any was closed; Copy copies the selected rows or all. Close Handles closes the row's handles in the holder and Close All Handles every handle to the zombie (`HandleNames::CloseInProcess`, type Process, after a confirmation); double-click or Go to Holder calls `GoToProcess`. Columns as in the other list tabs (`ColumnLayout`, the `ZombieColumns` setting, Zombie mandatory).
- **Object Types view** (`ObjectTypesView.*`, the tenth tab, Ctrl+0, `IDI_OBJECT`), as ObjectExplorer's: the kernel's object types from WinSys `ObjectTypes::Enum` (one `ObjectTypesInformation` query) with their counts and peaks, pool type and default charges, valid access mask, generic mapping (decoded by `AccessMaskDecoder`) and invalid attributes. Read on every tick, also while hidden; a count that changed since the previous refresh has its cell colored for that refresh (`Row::Change`, subitem custom draw: green up, red down; the other cells get back the colors the list chose for the row at the item stage, never `CLR_DEFAULT`, which is the system's black text even on a dark selection). The icons are the Handles page's (`GetHandleIcon`). The filter matches the name; columns as in the other list tabs (`ObjectTypeColumns`, Name mandatory).
- **Object Manager view** (`ObjectManagerView.*`, the eleventh tab, Ctrl+Shift+O, `IDI_OBJECTS`, `objects.ico`), as WinObj and ObjectExplorer: the object namespace from WinSys `ObjectNamespace`, a `CTreeViewCtrl` of directories (the root inserted when the tab is first shown; a node's subdirectories when it's first expanded, item data 1, `FillNode`; the selected directory's kept in step with its listing, `SyncNode`) beside a `CVirtualListView` list of the selected directory's objects, in a `CCustomSplitterWindow` that forwards both controls' notifications (the tree's handled by its ID, `TreeId`, before the list's handlers). The list is read again on every tick while the tab is active and merged by name: new objects green for two refreshes, removed ones red once; the selection is restored by name without scrolling to it, unless View > Keep Selection Visible (the Processes view's setting) is on (`ShowRows`' `ensureVisible`; a new directory, a filter or a header's sort shows it). Symbolic links' targets and creation times are read once per link; Handles is read for the rows shown (`ObjectNamespace::GetHandleCount`, an object opened by name with no access, else `MAXIMUM_ALLOWED`; only the types `ObjectNamespace::Open` knows: no devices or files), again on every refresh. Double-clicking (posted to the frame, which routes the command to the view) opens a directory, goes to a link's target (`GoToTarget`: its deepest directory in the namespace and the next component's row in it, clearing a filter that hides that row; also `IView::ShowObjectPath`, which the frame calls for a process sheet's Job page to open a silo's root directory), and opens anything else's properties: `CHandleSheet` on a handle this process opens by name (`MAXIMUM_ALLOWED`, else none; `ObjectNamespace::Describe` makes the `HandleEntry`; `SetSheetTitle` names the object rather than the handle, and `HideHandle` leaves out the handle's value and attributes, as the handle is the app's own, and that handle from the counts); the tree's context menu has the directory's Properties and Copy Path. Icons are the Handles page's (`GetHandleIcon`; `SymbolicLink` has `IDI_SYMLINK`), devices `IDI_DEVICE` and drivers `IDI_DRIVER`. The filter box matches the name, type and target. Rows are by name until a header is clicked. Settings: `ObjectManagerColumns` (Name mandatory), `ObjectManagerPath` (reopened at startup, as much of it as is still there) and `ObjectManagerSplitterPos`.
- **Pool Tags view** (`PoolTagsView.*`, the twelfth tab, Ctrl+Shift+P, `IDI_POOLTAGS`, `PoolTags.ico`), as PoolMonX: the kernel pools' usage by tag from WinSys `SystemInfo::GetPoolTagInformation` (one query), with paged and non-paged allocations, frees, their difference and the bytes in use, a total (hidden by default), and each tag's binary and description from WinSys `PoolTagDescriptions`: the Debugging Tools' `pooltag.txt` if installed (`FindFile`), else the copy built into the app (`IDR_POOLTAGS`, `res\pooltag.txt`, RCDATA); the status line says which. Non-elevated, the query succeeds with a single placeholder (tag `None`, every counter zero), which the view recognizes (`m_Withheld`): no rows, and the status line says elevation is needed. Read on every tick while the tab is active (also when it's activated, then without change marks, as it isn't read while hidden); a counter that changed since the previous refresh has its cell colored for that refresh, as on the Object Types tab. The filter matches the tag, binary and description; columns as in the other list tabs (`PoolTagColumns`, Tag mandatory).
- **Disk view** (`DiskView.*`, the thirteenth tab, Ctrl+Shift+D, `IDI_HARDDISK`, `Harddisk.ico`): file I/O per process and file from WinSys `FileIoTracker` (an ETW session on Microsoft-Windows-Kernel-File, elevated only, so the status line says why it's empty otherwise), acquired when the tab is first shown (`Recorders::AcquireFileIo`) and held until the view goes, as the RPC/ALPC tab's. Read and merged on every tick (also while hidden, for the rates), keyed by PID and file key: new rows green for two refreshes (not on the first read), rows the tracker forgot (a minute without I/O, or `RemoveProcess` for an exited process) red once. The rates are over the last three refreshes' counts (`RateUpdates`, a `History` per row), as the Network tab's, the events coming in batches about once a second. Until a header is clicked the rows are by PID and file key, as the tracker's order is a hash table's. A file the tracker couldn't name shows its file key (`(file 0x...)`): mostly System's lazy writes and paging I/O, whose file objects no process has a handle to. The filter box matches the process, PID and file; double-click or Go to Process calls `GoToProcess`; File Properties and Open File Location need a DOS path; Copy copies the shown columns. Columns as in the other list tabs (`DiskColumns`, Process mandatory).
- **Registry view** (`RegistryView.*`, the nineteenth tab, Ctrl+Shift+R, `IDI_KEY` until it has an icon of its own): the Disk tab's twin for the registry: operations per process and key from WinSys `RegistryIoTracker` (an ETW session on Microsoft-Windows-Kernel-Registry, elevated only, so the status line says why it's empty otherwise), acquired when the tab is first shown (`Recorders::AcquireRegistryIo`) and held until the view goes, merged on every tick as the Disk tab's (keyed by PID, key name and, for an unnamed key object, its address; new rows green, forgotten ones red), the rate being the operations a second over the last three refreshes. Columns (`RegistryColumns`, Process mandatory): process, PID, key (`HKLM\...`, `HKCU\...`, `HKU\...`; one the tracker couldn't name as `RegistryIoParser::UnnamedName` says why: `(kernel key 0x...)`, `(key 0x... of a protected process)`, `(key 0x..., closed)`, and a key opened relative to one as that name followed by the relative path), operations a second, opens (and creates), reads (queries and enumerations), writes (sets, deletes, new keys), failures (errors other than a buffer too small: mostly NAME NOT FOUND), the last operation, value and result (Process Monitor's words), and the first and last operation's times. The filter matches the process, PID, key and last value. The context menu: Go to Process (also a double-click), Open in Registry Editor (as the Autoruns tab's Jump: Regedit's `LastKey` and `regedit -m`; only for keys under HKLM, HKCU and HKU), Copy and Copy Key. The status line: keys with operations in the last minute, the operations a second, since when, and the events the session lost if any (`GetLostEvents`). Double-click or Details... opens `CEventDetailsDlg` (`EventDetailsDlg.*`, modal, resizable): the level's icon (the system's stock `IDI_ERROR`, `IDI_WARNING`, `IDI_INFORMATION`, and the app's `IDI_KEY` for audits as in the list (key.ico has 16 to 48 pixels), through `IconId`, at the static's size, `SS_REALSIZECONTROL` written as 0x40 as the resource compiler's headers lack it) and the source and ID as a bold title; the fields as borderless read-only edits in two columns (log, source, level, event ID, time, record ID, process with its name, thread, computer, keywords); the message in a scrolling read-only edit (CRLF line breaks; nothing selected and scrolled to the top on every change, as a read-only edit selects all its text when focused), or with Show XML the event's XML (WinSys `EventLog::GetXml`, read once per event, indented a line per element with an element's text kept on its line); Previous and Next walk the tab's rows through the view's callback, which moves the selection and returns a copy of the event (new events can arrive while the dialog is open, and `m_All` moves); Go to Process (while the process runs and started before the event); Copy (the fields as lines and the message, or the XML); Close. The view gives it the event's process name and the go-to through callbacks; Open in Event Viewer (`eventvwr.exe /c:"<log>"`); Alert on Events Like This... (`IMainFrame::AddAlertRule`: the alert rule dialog with the event's log, source and ID, a Security audit failure as the audit failure kind; added and saved on OK, as Options > Alerts would); Go to Process (enabled under the same condition as the process name); Copy (the row, with the whole message). The status line: counts of errors and warnings, how many arrived since the read, whether new ones are watched.
- **WSL view** (`WslView.*`, the eighteenth tab, Ctrl+Shift+W, `IDI_WSL`, `wsl.ico`): the installed WSL distributions (WinSys `WslDistros::Enum`, the registry's; docker-desktop's too, shown like any other) as root rows (name with "(default)", state, the base path in the Command Line column; a stopped one gray, a WSL 1 one said, as its processes are Windows pico processes in the Processes tab) and, under each running WSL 2 one, its Linux processes as a tree by parent. Which distributions run is asked by a `std::jthread` of the view's own every 5 seconds (`WslDistros::GetRunning`, wsl.exe, about 0.1 s; `WM_WSL_RUNNING` carries a `RunningState`; a `condition_variable_any` wait with the stop token, so `OnDestroy` stops and joins it at once): a `WslProcessMonitor` starts for each running WSL 2 distribution and goes when it stops (its processes then exit). On every refresh each monitor's last frame is taken and the next requested, so the rows lag a refresh and the UI never waits; `SyncProcesses` keys a process by distribution, PID and start (`Key`), computes CPU as the process's ticks against all of the VM's processors' ticks since the last frame, and its parent from the frame (a parent whose start is the frame's); `ArrangeTree` then puts each shown row under its parent while that's shown, else its distribution: a row whose place changed goes with its subtree (`DeleteItem` forgets the subtree's items, which the TreeListView deletes with it) and comes back parents first. Show Threads (the toolbar's check button right of the filter, `ID_WSL_SHOWTHREADS`, which comes to the view through the rebar; the `WslShowThreads` setting) asks the helper for the threads too (`Request(true)`, at once when it's turned on) and puts each process's threads under it (`m_Threads`, apart from `m_Processes` since a main thread's TID and start are its process's PID and start; `SyncThreads` with the same CPU share, the process's user; `IDI_THREADS`), before its child processes (inserted first, in TID order; sorting keeps them first whichever the direction): a thread's name is its comm, its TID in the PID column and its process's PID in Parent PID, with state, CPU, CPU time and start time; a frame asked for before it was turned on, without threads, leaves them as they are; turning it off deletes their rows. Terminate, Kill and Copy Command Line are for processes only (a signal goes to a thread's whole process). Columns (`WslColumns`; the usual header menu, Select Columns, Reset): process, PID, parent PID, user, state in words (`WslProtocol::StateName`), CPU %, CPU time, threads (a distribution's: its processes' total), memory (resident), virtual size, start time (from the VM's uptime), command line, processes (a distribution's). New processes green and exited ones red for the highlight's ticks. The filter matches name, PID, user, command line and distribution (a distribution's name shows all of its processes). The context menu: Terminate (SIGTERM) and Kill (SIGKILL), as root in the distribution (`WslDistros::Signal`, after a confirmation that warns for PID 1, the distribution's init), Copy and Copy Command Line. The status line: distributions, running, processes, threads, and the VM's memory in use. `OnDestroy` drains the poll's pending messages with `PeekMessage`, which returns `WM_QUIT` whatever the filter, and the frame posts it before its views are destroyed: one that's drained is posted again (else the app never exits). Tested on Ubuntu 26.04 (31 processes; the tree from systemd; start times as ps -o lstart; a test sleep terminated from the menu; Show Threads: 44 threads under their 31 processes, polkitd's four in TID order with their own names, gdbus, gmain and pool-spawner, the rows gone when it's turned off and back when it's turned on) and docker-desktop (busybox: its tree from wsl-bootstrap to dockerd).
